═══ 1. 選型理由 ═══
參考了兩個成熟的匿名身分方案（官方文件，來源附在報告後）：
- Supabase Anonymous Auth：匿名登入會在資料庫建一筆真正的 user（帶 is_anonymous
  旗標），權限掛在這個 user 身上；session 存在瀏覽器（JS client 存 localStorage，
  SSR 存 secure cookie）。只有登出、清除瀏覽資料、換裝置才會遺失。
- Firebase Anonymous Auth：web 預設是 LOCAL persistence，跨分頁同步；只有明確登出
  才會清掉。
兩者的共同模式：一個 user 記錄 + 一份持久憑證存在瀏覽器裡 + 權限是這個 user 的
屬性。沒有任何一家用「第二套獨立的 role session」。

結論：照這個模式在既有的 React + FastAPI + Neon 上自己實作，不引入
Supabase／Firebase。理由：
  (a) 現有的 owners 表本來就是 user 記錄，browser_identities 本來就是憑證表；
  (b) 引入外部服務要搬既有 owner 資料、加 JWT 驗證、多一個 vendor，違反
      「優先沿用既有技術」；
  (c) 需要的能力（持久憑證、權限欄位、跨分頁）用現有的表加一個欄位就夠。
