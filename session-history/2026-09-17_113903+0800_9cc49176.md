## 3. API credential provenance

**(a) Default API token（第三方 provider 憑證，例如 Market Data App）**

**(b) New Super User input（`ADMIN_SECRET`）**
- 儲存：`os.environ.get("ADMIN_SECRET")`，**完全不進任何資料庫表**，不跟任何 owner_id 綁定。
- 驗證路徑：`api_app/superuser.py::is_superuser(request, admin_secret=...)`，只比對 `Authorization` header 字串，**從不讀取、不參與 owner_id 解析**。

## 3. RoleSession 最終 schema

```python
@dataclass(frozen=True)
class RoleSession:
    token: str              # PK，不透明隨機字串，呼叫端生成
    role: str                # "superuser" | "superadmin"
    issued_at: str
    revoked_at: str | None = None   # None＝有效；非 None＝永久失效
```

無密碼雜湊／指紋／版本號欄位。Storage Protocol 三方法：
`create_role_session(session)`／`resolve_role_session(token) ->
RoleSession | None`（已撤銷或找不到皆回 `None`）／
`revoke_role_session(token, *, now) -> bool`（`now` 由呼叫端傳入，
比照既有 `touch_browser_identity()`／`touch_owner_activity()` 的
既有分工，Storage 層不自己讀時鐘）。

# AUTH-02 IMPLEMENTATION — Completion Report

## 1. Implementation Summary

Built the single role-judgment point (`Role`: `normal < superuser <
superadmin`, all four comparison operators hand-written — a real
footgun was caught mid-implementation where `functools.total_ordering`
silently fell back to lexicographic string comparison because `Role`
mixes in `str`, which already provides `__le__`/`__gt__`/`__ge__`) in
`api_app/superuser.py`, alongside `resolve_role()`/`require_role()`.
Wired three new HTTP endpoints in `api_app/main.py` for login, logout,
and status query, plus a persistent, independent `__Host-oc_role`
cookie. The existing two-tier `is_superuser()`/`require_superuser()`/
`ADMIN_SECRET` mechanism (PB-09) is completely untouched — both
mechanisms coexist this round; retiring `ADMIN_SECRET` and wiring
existing `/api/superuser/*` etc. endpoints to `require_role()` is
AUTH-03 (#310)'s job, per the ticket's explicit non-goals.

## 2. API Endpoints

- `POST /api/auth/login` — body `{"password": str}`. Compares against
  `SUPERADMIN_PASSWORD` then `SUPERUSER_PASSWORD` via
  `secrets.compare_digest` (constant-time). On a hit, creates an
  AUTH-01 `RoleSession` and sets the cookie; returns `{"role": "..."}`.
  No match (wrong/empty password, or both env vars unset) → 401
  `{"detail": "unauthorized"}`, indistinguishable across all failure
  reasons. Missing `password` field → 422 (standard FastAPI/pydantic
  request validation, never reaches password-comparison logic, so it
  cannot leak anything about password correctness).
- `POST /api/auth/logout` — revokes the session server-side
  (`revoke_role_session`) if a cookie is present, then clears the
  cookie. Always 200, `{"role": "normal"}`, including when called with
  no cookie or an already-revoked one (graceful repeat logout).
- `GET /api/auth/status` — unconditionally 200,
  `{"role": "normal" | "superuser" | "superadmin"}`. Never requires
  proof of identity to query identity (mirrors the existing
  `/api/superuser/status` rationale).

All three are registered under `/api/auth/*`, added to
`_OWNER_EXEMPT_PREFIXES` — none of them create or touch an anonymous
owner as a side effect.

## 3. Role-Resolution Behavior

`resolve_role(request, *, resolve_session)`:
- No cookie → `Role.NORMAL`.
- Cookie present but `resolve_session(token)` returns `None` (unknown
  or revoked token) → `Role.NORMAL`.
- Cookie present, session found, `revoked_at is None` → trusts the
  stored `role` field directly, no secondary password check.
- Malformed/unknown `role` string in a resolved session (structurally
  unreachable today since `auth_login` is the only writer, always
  using an enum value) → falls back to `Role.NORMAL` rather than
  raising.

`require_role(request, minimum, *, resolve_session)` raises 401 when
the resolved role is below `minimum`, without distinguishing "no
cookie" from "cookie present but insufficient role" — identical
external behavior for both. It has zero existing callers this round
(deliberately — wiring it up is AUTH-03/04/05's job).

## 4. Actual Cookie Settings

Confirmed via a live `TestClient` `Set-Cookie` header:

```
__Host-oc_role=<32-byte-urlsafe-token>; HttpOnly; Max-Age=34560000; Path=/; SameSite=lax; Secure
```

- `Max-Age=34560000` seconds = 400 days, identical to and reusing the
  existing `_OWNER_COOKIE_MAX_AGE_SECONDS` constant.
- No `Domain` attribute (required for `__Host-` prefix compliance).
- Set **once**, at login time only — deliberately does **not** get
  sliding-window renewal on every subsequent request the way the owner
  cookie does (that logic lives in the shared
  `_call_within_owner_scope()` middleware; teaching that middleware
  about the role cookie/session lookup would violate spec §19's "no
  shared function or intermediate result between axis-1 and axis-2").
  This still satisfies the AC (cookie survives a simulated browser
  restart, verified by test) — it just means a role session's absolute
  lifetime is capped at 400 days from login rather than extended by
  ongoing use. `Expires` is derived from `Max-Age` by the client, not
  set as a separate explicit header field.
- Logout uses `response.delete_cookie(..., path="/", httponly=True,
  secure=True, samesite="lax")`.
