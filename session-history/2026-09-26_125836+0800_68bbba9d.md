## Part B — 建立 Anti-Abuse Prototype

模擬以下三層防護：

### Layer 1 — owner bucket
cookie owner 的 expensive vendor-fetch quota。

目的：
正常使用者刷新不受影響，但單一 owner 不可無限燒 vendor。

### Layer 2 — source/IP bucket
建立「不依賴 cookie」的 abuse bucket prototype。

要求：
- IP 只作 abuse control，不作資料 identity。
- 不得因 IP 改變而換 owner。
- prototype 可使用 fake IP。
- 評估 raw IP vs HMAC/hash ephemeral key。
- 必須有 retention / cleanup 概念，不永久保存 IP identity。

至少模擬：
- per-minute burst
- per-hour / per-day budget
- NAT/shared-IP 情境

### Layer 3 — global vendor fuse
保留既有 global fuse，作最後成本上限。

分析 Layer 1 + Layer 2 是否能讓正常情況幾乎碰不到 global fuse。

## Part C — Cookie reset attack

實際模擬：

1. owner A 用到 quota
2. 刪 cookie
3. 建 owner B
4. 同 IP 繼續打
5. 重複多次

確認：
- 單純刪 cookie 不能恢復完整 vendor budget。
- DB 會產生多少垃圾 owner。
- 攻擊成本與能造成的 vendor calls。

再模擬：

- 換 IP、cookie 不變
  → owner quota 必須仍存在，scenario ownership 不得消失。

- cookie + IP 都輪替
  → 說明剩餘 attack surface，以及 global fuse 最壞保護效果。

## Part D — Popular ticker dedupe prototype

重點測「同一 ticker 大量重複分析」能否大幅降低 upstream calls。

Prototype 兩種方案：

A. single-flight dedupe
- 同一時刻 100 個 AAPL request
- 第一個真的抓 upstream
- 其他等待並共用該次結果
- 不永久儲存 chain payload

B. very-short TTL reuse（只模擬，不正式實作）
- 例如 10s / 30s / 60s
