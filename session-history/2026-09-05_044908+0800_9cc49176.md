A. User Isolation Boundary

Research 發現目前：

* 無 auth / user ownership
* list_scenarios() 等於全站 scenarios
* 開站 refresh 全站 scenarios
* multi-user 下可能形成 O(U²)
* 同時存在 privacy / correctness 問題

* Initial multi-user ownership model 最小需要什麼？

    * ownership/data boundary
    * authentication product layer
        兩階段？
* anonymous / single-owner transition 如何處理既有資料？

不要因「未來可能多租戶」就設計 enterprise RBAC / org / team。

B. Result / Snapshot Storage Lifecycle

Research 發現：

* results.view 單列可達約 12.18 MiB
* 約 96.4% 來自 all_candidates
* refresh 每次新增 row
* results / snapshots 無 retention
* result_history() 可能全量讀巨大 view

請收斂：

1. Current result

UI 真正需要保存哪些資料？

2. Historical result

歷史上真的需要保存哪些資料？

3. Heavy analysis artifacts

例如：

* all_candidates
* full matrices
* raw chain snapshot

應該：

* 永久存？
* 短期存？
* 只保存 current？
* 拆表？
* 壓縮？
* object storage？
* 完全不保存？

不要先假設答案。

核心問題：

「為了之後能查歷史」到底需要保存 complete analysis，還是只需要保存少數 canonical historical facts？

請特別避免因方便 debug 就永久保存大量 production payload。

C. Option Chain Shared Lifecycle

Research 發現：

* Cboe whole-chain fetch
* 跨 invocation / user 零共享
* 已實測 HTTP 429
* 429 沒有 Retry-After/backoff/circuit breaker
* production fallback 不可達

請收斂：

Freshness Contract

Option chain 到底允許多舊？

例如：

* 5 秒
* 15 秒
* 30 秒
* 1 分鐘
* 使用者手動 refresh 必須強制 fresh？

不要憑直覺選數字，要從產品語意推導。

Sharing Scope

是否應：

symbol + fetched_at bucket -> shared chain snapshot

使 request load 更接近：

unique active symbols × refresh frequency

而不是：

users × scenarios

Cache location

比較：

* process-local memoization
* Neon
* Redis / KV
* object/blob storage
* hybrid

考慮：

* chain 1–5+ MB
* serverless concurrency
* cold starts
* latency
* storage cost
* distributed single-flight

Stampede

同一時刻 100 人 refresh TLT，理想上 vendor 應收到多少 request？

定義：

* lock
* lease
* single-flight
* stale-while-refresh
* timeout

429 semantics

明確定義：

* honor Retry-After
* backoff
* circuit breaker
* stale fallback
* user-facing state
* manual retry 是否禁止立即重打 vendor
