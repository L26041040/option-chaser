     → claim_browser_token（以 token PK 防重複，原子建立 owner +
       browser_identity）
   D 發 cookie
     → set_cookie(__Host-oc_owner, HttpOnly, Secure, SameSite=Lax,
       Path=/, Max-Age=(180+7)d) + X-OC-Owner-Bound:1
     → 前端 markOwnerBound()：bound=true，刪除 IDB 與 localStorage 的
       bootstrap token。從這一刻起 cookie 是唯一憑證。
   E/F 關閉後重開
     → 同源 fetch（預設 credentials:same-origin）帶 cookie
     → resolve_owner_by_token → touch_browser_identity(last_seen_at)
     → 每次回應都重新 Set-Cookie 續命（187 天滑動窗，有效）
   G/H 清單
     → list_scenarios(owner)，只依 owner 過濾
     → 沒有自動封存、沒有快取、沒有其他隱藏路徑
   I SU / SA 登入
     → /api/auth/login 只發 oc_role cookie（豁免 owner middleware）
     → logout 只清 role cookie，不碰 owner cookie
     → 角色與 owner 正交：登入 SU 永遠不會換成另一個 owner 的清單
   J cookie 遺失後再建立
     → 新的 bootstrap token → 默默建立第二個 owner（ghost owner）
     → 舊 owner 與舊劇本永久存取不到
     → 舊 owner 因為有資料，要 187 天後才會被清理

5. Root cause ranking（只看這次事件）
   - CONFIRMED：伺服器沒有刪除資料。四筆劇本在 10/21 仍存在。
     cleanup 對有資料的 owner 要 180+7 天才判可刪；沒有 auto-archive。
   - CONFIRMED：SU 登入看不到劇本是設計如此（角色 ≠ owner），
     不是第二個 bug。
   - VERY LIKELY：那次開站的請求沒有帶到 KoFnasxT 的 cookie
     （唯一能讓清單變空的路徑）。要由 Q2 確認。
   - POSSIBLE（各有已知機制，但都沒有這次事件的直接證據，不當結案理由）：
     a. 不同的 cookie jar：iOS 主畫面 Web App 與 Safari 的儲存是分開的。
        index.html 有 apple-mobile-web-app-capable=yes，支援加到主畫面；
        另外 LINE / FB 等 App 內建瀏覽器、Chrome iOS 也各自一份。
     b. 不同的 hostname：Production / Preview / 單一部署 URL 共用同一個
        DB，但 __Host- cookie 依 host 各自一份。PR 留言裡的「Visit
        Preview」連結就是其中之一。
     c. 無痕瀏覽分頁被關閉。
     d. 使用者或系統清除網站資料。
   - RULED OUT：
     - 伺服器在同一個 jar 用新 token 覆寫 cookie：只有已綁定才會
       Set-Cookie，而且送回的是同一顆 token。
     - 部署造成：期間沒有部署，部署也不影響 cookie。
     - Max-Age 太短：187 天滑動。
     - Safari ITP 的 7 天上限：時間尺度不符（數小時），而且那個上限
       針對的是 script-writable storage 與第三方情境。
     - memory storage fallback：health 回 postgres，而且資料仍在 DB。
     - cleanup 誤刪：資料仍在。
   - UNKNOWN：實際是 a / b / c / d 哪一種。

6. Bootstrap / Cookie findings
   - [設計缺陷] 一綁定就刪掉本機的 bootstrap token，伺服器也只在綁定後
     10 分鐘內接受它。原意是避免 localStorage 變成第二個身份載體，
     代價是零備援：cookie 一掉就救不回來。
   - [設計缺陷] X-OC-Owner-Bound 只代表伺服器送出了 Set-Cookie，
     不代表瀏覽器真的存住了。前端沒有任何「存住了沒」的回讀確認。
   - [UX 缺陷] cookie 不在時，清單直接顯示「還沒有劇本」，沒有任何
     「這個瀏覽器以前有身份」的偵測或提示。
   - [設計缺陷] 遺失 cookie 後只要寫入一次，就會默默建立新 owner；
     使用者從此在新 owner 上工作，舊資料等於永久隔離。
   - 正確的部分：
     - __Host- 屬性齊全（Secure / Path=/ / 無 Domain）
     - SameSite=Lax 不影響同源 fetch
     - 187 天滑動續命確實生效（每個綁定回應都重發）
     - 多分頁的競態已用 IndexedDB transaction + Web Locks 處理，
       並有 e2e 覆蓋
     - module-level 的 bound 狀態只存在單一分頁的記憶體：重新載入就
       歸零，不會發生「cookie 不見了 bound 卻還是 true」而跳過綁定
       （寫入仍會帶新的 bootstrap token）

7. Role / Owner architecture findings
   - 軸一（owner cookie）與軸二（role cookie）完全正交，這部分是安全的：
     共用的 SU 密碼拿不到任何特定 owner 的身份。
   - SA 可以透過 /api/superuser/owners/{id}/scenarios 唯讀看到別人的資料，
     PB-03 的 migrate_owner 原語也存在。但沒有，也不應該有「憑 SU 或 SA
     密碼就把某個 owner 綁到目前瀏覽器」的產品路徑：共用密碼證明不了
     某個 owner 是誰的。
   - 結果：就算大哥本人是 Operator，目前也只能用一次性的人工 DB 操作
     救回自己的資料；一般使用者完全沒有自救途徑。

8. External research（來源列在報告後）
   - Supabase 官方：匿名使用者「登出、清除瀏覽資料、換裝置」就無法再存取
     帳號；解法是連結 email 或 OAuth，轉成永久使用者。
   - Firebase 官方：匿名帳號定位為暫時性，用 link 連結登入方式，之後才能
     在未來的 session 繼續存取資料；連結後也免於自動清理。
   - MDN：__Host- cookie 不帶 Domain，只屬於設定它的 host，子網域與其他
     host 都看不到。
   - Vercel：每個部署都有自己的 URL（commit URL、branch URL、production
     URL 是不同的 hostname）。
   - WebKit / WWDC23：主畫面 Web App 不屬於 Safari，有自己的 cookie 與
     儲存；只在加入主畫面那一刻複製一次 cookie。WebKit bug 181849 中
     維護者確認這是刻意設計。
   - OWASP：持久 cookie 會存在磁碟直到到期；Domain 建議不設定（限縮在
     origin）；權限變更後必須重發 session ID。
   - 業界結論：成熟產品不會把「匿名 cookie 是唯一憑證」當作長期資料的
     保存方式。它們一律提供使用者自己能持有的第二把鑰匙：連結 email /
     OAuth，或可備份的還原碼。

9. Three solution options
   A. 還原碼（Recovery Key）＋遺失偵測。
      做法：
        - 伺服器為每個 owner 產生 ≥128-bit 的還原碼，只存 hash。
        - 使用者在 Settings 顯示、複製或下載，可以隨時重發（舊的作廢）。
        - 在任何瀏覽器貼上還原碼 → 伺服器替這個瀏覽器發一個新的
          browser_identity 指向原 owner（rate limit + audit）。
        - 前端在非身份性的 localStorage 留一個「曾有身份」標記，cookie
          不在時顯示「這個瀏覽器的身份不見了，輸入還原碼可找回」，不再
          顯示空清單。
      評估：
        - 能解決這次問題：可以（未來遺失時自救）
        - 能避免再發生：遺失仍會發生，但不再等於資料消失
        - 能恢復既有資料：可以，只要在 cookie 還在時先產生還原碼；
          已經遺失的舊資料仍需一次性的 Operator 處理
        - Security：還原碼是 bearer secret，等同密碼；高熵、只存 hash、
          暴力嘗試有 rate limit
        - UX：多一個「備份還原碼」步驟（建立第一個劇本後提示）
        - 複雜度：中低（1 張表或 1 個欄位、2 個端點、Settings UI）
        - Migration：低（純加法，不動既有 cookie）
        - 對 Normal / SU / SA：Normal 多了自救能力；SU / SA 角色模型完全不變
   B. 連結 email（magic link 驗證）。
      評估：
        - 跨裝置、可恢復、最接近 Supabase / Firebase 的標準做法
        - 需要寄信服務、驗證流程、個資與隱私政策更新，還要處理 email
          更換、帳號合併
        - 複雜度：中高
        - Security：要防 email enumeration 與連結攔截
        - 適合等 Beta 之後真的需要跨裝置同步時再做
   C. 只做強化、不做還原：
      - 正式網域的 canonical redirect；Preview 加上明顯的
        「非正式站，資料不互通」橫幅
      - 遺失偵測加上提示
      - Operator 用的 audited 一次性 rebind runbook
      評估：
        - 複雜度最低，能讓問題看得見
        - 但使用者仍然無法自救，cookie 一掉照樣只能求助 Operator
        - 治標不治本

10. Recommended solution
   - A 為主，搭配 C 裡的 canonical host 與遺失偵測；B 保留為之後的升級
     路線。
   - 這次事件的舊資料：以 Q1–Q3 確認 KoFnasxT 確實是大哥本人建立的
     （以劇本內容 SPCX / TLT / ORCL / TSLA 和建立時間比對，不靠「時間
     相近」推論），再由大哥以 Operator 身份裁示，做一次 audited 的
     migrate / rebind 到大哥目前的 owner。這只是一次性處理，不做成
     「SU 密碼就能取回」的產品功能。

     - Playwright 全部用 routeLibrary mock 掉 /api，從來沒有真的
       Set-Cookie。
     - 後端 TestClient 的 cookie jar 只活在單一 client 裡，沒有
       「關閉瀏覽器再開」。

     ① Playwright 接真後端：用 launchPersistentContext(userDataDir)
       建立劇本 → 關閉瀏覽器 → 用同一個 profile 重開 → 劇本還在。

     ② 在同一個 profile 清掉 cookie、保留 localStorage 標記
       → 顯示遺失提示（不是空清單）→ 輸入還原碼 → 劇本回來。
     ③ 改用另一個 host（localhost ↔ 127.0.0.1）模擬 hostname 切換
       → 顯示遺失提示或 canonical redirect，不會默默建立新 owner。
     ④ 兩個分頁：一個綁定後，另一個不會建立第二個 owner（已有，
       改接真後端再驗一次）。
     ⑤ SU 登入前後清單一致；登出不影響 owner cookie。
     ⑥ 後端重啟（模擬部署）前後，同一顆 cookie 解析到同一個 owner。
     ⑦ 後端：還原碼只能綁到它自己的 owner、錯誤嘗試有 rate limit、
       重發後舊碼失效、audit 有紀錄。
