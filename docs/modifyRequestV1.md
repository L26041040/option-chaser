一、產品目的

Option Chaser 是一個網頁版選擇權劇本分析工具。

使用者有自己的市場判斷能力，不需要系統預測價格。

使用者輸入：

* 標的代號
* 目標價
* 預計達成的年份與月份

例如：

TLT 在 2028 年 1 月左右到達 105。

系統負責探索合適的選擇權到期日與 Call Debit Spread，找出在這個劇本下收益率最高的組合。

⸻

二、首頁與輸入方式

桌面版首頁預期採用：

左邊20%寬度：已保存的劇本清單
右邊80%寬度：新增劇本區/劇本檢視區


使用者不需要登入，打開網站後直接進入可操作的首頁。

新增劇本只要求：

1. 標的代號
2. 目標價
3. 預計達成年月

年份與月份必須使用同一個輸入框。

輸入框需要理解例如：

2028/1
2028/01
28/1
28/01

以上格式應正規化為同一個年月。

這個年月代表使用者預計標的到達目標價的時間，不是要求使用者自己選擇選擇權到期日。

使用者不需要輸入：

* 選擇權到期日
* 買入履約價
* 賣出履約價
* Spread 寬度

三、到期日探索與 Spread 排名

建立劇本後，系統應探索目標月份附近約五個具有代表性的選擇權到期日。

例如：

30 Jun 2027
16 Jul 2027
21 Jan 2028
16 Jun 2028
15 Dec 2028

到期日挑選規則（2026-07-30 已確認，取代原「列為後續研究事項」）：

1. 使用者輸入的是「目標年月」，不是指定單一選擇權到期日。
2. 先以該月份的第三個星期五作為日曆錨點。
3. 從市場實際存在的選擇權到期日中，找出距離該錨點最近的實際到期日作為
   baseline；若距離相同，選擇較晚的到期日。
4. 再以 baseline 為中心，挑選最多五個實際到期日。
5. 預設選取 baseline、前方最近兩個、後方最近兩個；若某一側數量不足，
   從另一側依距離補足。
6. 每一個被選中的實際到期日，都要各自完整窮舉符合條件的 Call Debit
   Spread，並各自產生排名結果。

第三個星期五只是用來定位探索中心的日曆錨點，不代表系統必須直接使用該日
作為唯一 expiry，也不是把使用者輸入的月份映射成月底或某個固定結算日。

主要排名情境維持簡單：

* 假設標的在該 Spread 到期時等於使用者輸入的目標價。
* 假設將 Spread 持有至到期。
* 依照相對於建倉淨支出的百分比收益率排名。

排名以「每個到期日各自排名」為單位（2026-07-30 已確認，取代原
「跨到期日合併取全域前十名」的錯誤模型）：

1. 每個被選中的到期日，各自產生自己的 Top 10。

   例如 baseline 到期日 2028/01/21 的 Top 10：

   #1｜買入 102 Call／賣出 105 Call｜收益率 2627%
   #2｜買入 101 Call／賣出 104 Call｜收益率 2410%

2. 每個到期日摘要只顯示該期的第 1 名，供使用者快速比較不同到期日。

   每個到期日的第 1 名需要附上 Heatmap 縮圖。

不採用「五個到期日全部候選合併後取跨到期日全域 Top 10」作為主要模型。
詳細頁的兩層結構見第八節。

四、Heatmap

每一個排名結果都應有自己的 Heatmap。

使用者可以點擊排名結果或 Heatmap 縮圖，查看詳細 Heatmap。

Heatmap 顯示該 Spread 在不同：

* 未來日期
* 標的價格

組合下的預估收益率。

Heatmap 與排名的用途不同。

排名仍使用：

目標價、持有至 Spread 到期的收益率。

Heatmap 則必須正確呈現到期前的理論價值，包括買入腿與賣出腿剩餘的時間價值。

不可把到期 payoff 公式直接套用到所有 Heatmap 日期。

例如標的同樣到達 105：

* 今天到達
* 半年後到達
* 到期時到達

可能顯示不同的 Spread 收益率。

Heatmap 計算行為需要研究及比對：

https://www.optionsprofitcalculator.com/calculator/call-spread.html

Heatmap 的價格範圍不能停在使用者輸入的目標價。

至少需要延伸至目標價以上 15%，讓使用者查看超額達標時的結果。

這項 Heatmap 修正不得改變原本的 Spread 排名公式。

五、劇本卡片

首頁左側以緊湊卡片顯示已保存劇本。左側顯示的是劇本清單，不是 Spread
清單。

排序規則（2026-07-30 已確認）：

每個劇本完成刷新後，取該劇本此次完整分析結果中的最高收益率，作為該劇本
在左側清單中的排序值。左側劇本清單依各劇本的最高收益率由高至低重新排序。

例如：

* 劇本 A 最高收益率 520%
* 劇本 B 最高收益率 310%
* 劇本 C 最高收益率 180%

左側排序即為 A、B、C。

黃燈劇本使用上一份完整成功快照中的最高收益率排序。

紅燈（目標月已過完）劇本一律沉底，排在所有綠燈與黃燈劇本之後
（2026-07-30 已確認）。

左側清單提供編輯工具，使用者可手動移除劇本（2026-07-30 已確認）。
沉底的紅燈劇本由使用者自行決定何時移除，系統不自動刪除。

每張卡片只放必要資訊：

* 標的
* 目標價
* 預計達成年月
* 目前最高的「目標達成並持有至到期收益率」
* 一個資料狀態燈號

卡片不應塞入：

* 完整 Spread 腿資訊
* 長篇說明
* 大量技術數字
* 完整錯誤訊息

收益為正時使用綠色。

收益為負時使用紅色。

點擊卡片後，進入該劇本的詳細分析頁。

六、資料狀態燈號

每張劇本卡片只有一個燈號。

綠燈、黃燈、紅燈都是「劇本級」狀態。正常情況下，一個劇本不會同時出現
部分到期日綠燈、部分到期日黃燈。

綠燈

本次劇本完整刷新成功，產生一份可信且完整的新快照。

黃燈

本次刷新中的關鍵資料取得或分析失敗，無法產生完整可信的新快照。

此時：

* 丟棄本次所有部分結果。
* 完整保留上一份成功快照。
* 顯示上次成功更新時間。
* 整個劇本顯示黃燈。

紅燈

使用者輸入的目標月份最後一天已經過完。純日曆判定，不依賴市場資料。

紅燈優先於綠燈與黃燈。

個別 Option 沒有有效報價的處理：

個別 Option 沒有有效 bid、ask 或其他必要報價時：

* 排除該 Option。
* 所有依賴該 Option 的 Spread 不列入計算。
* 不得用不準確或缺失的價格硬算收益率。

但少數個別 Option 沒有報價，不等於整個劇本刷新失敗。只要所有必要到期日
的 option chain 成功取得，且剩餘有效資料足以完成可信分析，劇本仍可成功
刷新並顯示綠燈。

必須區分：

* 個別無效報價：正常候選過濾，不影響燈號。
* 整個到期日 chain、標的價格或其他關鍵資料取得失敗：劇本級刷新失敗，
  顯示黃燈。

七、動態更新

刷新的單位是「劇本」，不是個別 Spread。

系統沒有 Spread API。Spread 是由 Option API 取得的基礎資料即時計算而成。
因此每次刷新都必須重新計算該劇本的全部有效候選，否則無法知道原本未入榜
的 Spread 是否已成為新的第一名。

不得只刷新曾入榜、曾顯示或曾被追蹤的 Spread。

刷新一個劇本的流程：

1. 取得標的最新價格。
2. 依既定六點規則找出最多五個實際到期日。
3. 取得這些到期日的完整選擇權基礎資料。
4. 排除沒有有效報價、無法可靠計算成本的個別 Option。
5. 由其餘有效 Option 重新組合所有符合條件的 Call Debit Spread。
6. 同時重新計算符合條件的 Long Call。（2026-07-30 確認：MVP 階段本步驟
   暫不執行，隨第九節 Long Call 比較功能一併生效，見附錄A8.3。）
7. 計算成本、目標情境收益、報酬率等指標。
8. 每個到期日各自重新排名。
9. 產生完整的新劇本結果快照。
10. 成功後整組替換上一份快照。

自動刷新與手動刷新：

* 打開網站後，自動刷新所有尚未過期的劇本。
* 同一個 Streamlit session 只在首次載入時自動刷新一次。
* 一般切頁、點擊卡片、切換到期日或展開內容，不得再次自動呼叫 API。
* 左側劇本清單旁新增一個常見的網頁刷新圖示按鈕。
* 使用者點擊此按鈕時，重新刷新所有尚未過期的劇本。

例如 TLT 目前價格從 85 上升到 95 後，排名前面的 Spread 可能改變。

建立劇本時的第一名不可永久固定。

某一個劇本更新失敗，不應阻止其他劇本更新。

八、Spread 詳細頁與歷史

點擊劇本卡片後，詳細頁採兩層結構（2026-07-30 已確認）：

第一層：到期日摘要

* 被選中的到期日（至多五個，依第三節六點規則）都顯示。
* 每個到期日只顯示該期最高收益的第 1 名結果，供使用者快速比較不同
  到期日。
* 每個到期日第 1 名附 Heatmap 縮圖。

第二層：所選到期日的詳細排名

* 預設選中 baseline，也就是最靠近目標月份日曆錨點的實際到期日。
* 下方詳細列表預設顯示 baseline 該期自己的 Top 10。
* 使用者點擊其他到期日後，下方才切換成該到期日自己的 Top 10。

詳細頁另應顯示：

* 劇本摘要
* 被選中 Spread 的詳細 Heatmap
* 被選中 Spread 的歷史紀錄

同一個 Spread 的身份至少由下列資料辨識：

* 標的
* 到期日
* 買入履約價
* 賣出履約價

同一個 Spread 即使：

* 排名上升
* 排名下降
* 掉出 Top 10
* 後來重新進入 Top 10

都應延續同一份歷史紀錄。

每次成功更新市場資料時，至少保存：

* 更新時間
* 當時標的價格
* 當時 Spread 建倉淨成本
* 當時依相同排名公式計算的收益率
* 當時排名

MVP 不要求保存每一次完整 Heatmap 快照。

（上述「掉出 Top 10／重新進入 Top 10」指該 Spread 所屬到期日自己的
Top 10。）

歷史保存與刷新必須分離（2026-07-30 已確認）：

「歷史要保存哪些結果」不得影響每次刷新的計算範圍；每次刷新一律重新計算
該劇本所有有效候選。

歷史保存範圍（2026-07-30 已確認）：每次成功刷新，保存**該次全部有效候選**
的歷史欄位（更新時間、標的價格、建倉淨成本、收益率、所屬到期日內名次），
不只保存入榜者。完整 Heatmap 快照仍不保存（維持前述 MVP 限制）。後續再
依實際需求縮減不必保存的部分。全量保存下，同一 Spread 的歷史唯一可能的
斷點是「該候選當次不再有效」（如缺報價被過濾）。

原子更新：

劇本更新必須採完整快照原子性：

* 要嘛完整新快照成功產生並整組替換。
* 要嘛本次刷新失敗，完整保留上一份成功快照。

嚴禁混合：

* 今天的標的價格
* 今天部分到期日資料
* 上次其他到期日資料

也不得使用部分成功結果重新排名。

保留上一份完整快照雖然不是最新資料，但同一份快照中的標的價格、Option
報價、Spread 計算與排名彼此一致，因此仍比混合新舊資料可靠。

九、Long Call 比較

系統還應能比較：

Long Call 最多必須用多少價格買入，才能在相同目標價及持有至到期情境下，追上所選 Spread 的收益率。

這項比較不改變首頁輸入方式。

使用者不需要在首頁先選 Long Call。

請稽核舊版目前是否已經具有可重用的 Long Call 計算能力，以及加入此比較需要多少修改。

若此功能尚未接近完成，請在路線圖中清楚分離為核心 Spread MVP 完成後的下一個小步驟，不得因此擴大或阻塞核心 MVP。

十一、手機版與 UI 實作原則

網站需要能在手機上完整操作。

手機版不需要維持桌面版的 20%／80% 左右排列，但必須保留：

* 劇本清單
* 新增劇本
* 狀態燈號
* Top 10
* 各到期日第一名
* Heatmap 縮圖
* 詳細 Heatmap
* Spread 歷史

不需要在手刻 CSS 美化上投入大量工程。

視覺設計可以後續交由 v0 或其他 AI UI 工具產生，再與現有功能結合。

本次稽核要判斷現有 UI 是否能簡化或局部替換，不要只因為外觀不理想就直接判定整個前端重寫。

十二、未來 Agent API 邊界

核心分析能力未來應能由 ChatGPT、Claude 或其他 agent 呼叫。

請稽核目前的計算邏輯是否與 UI 分離，是否能在未來提供版本化 API。

本次 MVP 不要求完成：

* Agent 對話介面
* 對外商業 API
* AI 自動建立劇本
* AI 預測價格

不可只為了未來 API，現在就建立微服務或複雜分散式架構。

附錄A、產品決策紀錄（2026-07-30 Grill 會議）

本附錄記錄需求方在 Grill 過程中確認的產品決策，效力等同正文。

A1. 到期日探索規則 — 已確認，內容見第三節（六點規則）。

A2. 日期語意分離原則 — 已確認。

使用者輸入的年月不得被映射為單一內部日期後供所有用途共用。下列四個
日期語意各自獨立決定，不得因現有 AnalysisParams.target_date 是單一日期
型別而合併；資料型別遷就產品語意，反之不可。

1. 到期日探索中心 — 已確認：日曆錨點＝目標月份的第三個星期五（見 A1）。
2. Spread 排名估值日 — 已確認：各 Spread 自身的到期日。此為第三節
   「假設標的在該 Spread 到期時等於目標價、持有至到期」之既有定義，
   估值即該到期日的內在價值（payoff），不使用任何共用日期。
3. Heatmap 日期軸 — 已確認：每個 Spread 的 Heatmap 日期範圍為
   「今天 → 該 Spread 自己的實際到期日」。舊版在日期軸上以單一
   target date 標記 * 目標欄的做法屬舊實作細節，非本需求文件之必要
   功能；列為可移除、或日後另行確認的非阻塞顯示項目，不得反向要求
   把 target month 映射成單一日期。
4. 紅燈「劇本年月已過期」判定日 — 已確認：目標月份最後一天過完即為
   過期。純日曆判定，不依賴市場資料；紅燈優先於黃燈。

A3. 核心資料模型 — 已確認。

持續刷新與保存的主要單位是「劇本」，不是個別 Spread。一個劇本由標的、
目標價、目標年月三項構成。

每次刷新劇本時，都必須重新取得該劇本所需的完整選擇權基礎資料，再由系統
重新推算所有 Spread 與 Long Call 的成本、收益率及排名。

系統沒有 Spread API。Spread 是由 Option API 取得的基礎資料即時計算而成。
因此不得將「哪些 Spread 要持續追蹤」與「每次刷新要計算哪些 Spread」混為
一談。

刷新單位、燈號單位、原子更新單位全部都是「劇本」。

A4. 排名結構 — 已確認：每個到期日各自 Top 10（見第三節、第八節）。
「跨到期日全域 Top 10」不再是主要詳細頁模型。

A5. 劇本持久化欄位 — 已確認。

劇本保存的是「目標年月」，不是目標日期。持久化欄位為
`Scenario.target_month`（YYYY-MM），直接取代原 `target_date`
（YYYY-MM-DD）；不保留兩個日期欄位並存，避免再次成為「把年月補成
某一天」的溫床。既有已持久化劇本依 `schema_version` 遷移。

劇本 ID 格式不受影響：現行 `scenario_id()` 本來就只取年月組成
`{symbol}-{price}-{yyyymm}`，已是月粒度。

由此衍生、同批確認的語意：

* 「目標時間已過」的驗證與判定一律為月級（目標月最後一天過完），
  不得再使用「目標日 ≤ 今天」這類日級判斷。
* 到期日下限不得再以「到期日 ≥ 目標日」硬性過濾。六點規則明確要求
  選取 baseline **前方**最近兩檔到期日，那些到期日可能早於目標月；
  硬性下限會使六點規則無法實作。

A6. 左側清單操作 — 已確認（2026-07-30）。

* 紅燈劇本一律沉底，排在綠燈與黃燈劇本之後。
* 左側清單提供編輯工具，使用者可手動移除劇本；系統不自動刪除紅燈劇本。

A7. 歷史保存範圍 — 已確認（2026-07-30）。

每次成功刷新保存該次全部有效候選的歷史欄位（見第八節），不只保存入榜者；
完整 Heatmap 快照仍不保存。後續依需求縮減。

A8. 批次決策 — 已確認（2026-07-30，Grill 收尾，一次定案）。

1. 建立劇本當下立即觸發該劇本的首次刷新。尚無任何成功快照的劇本，
   卡片收益率顯示「—」，左側排序列於所有持有快照的綠／黃燈劇本之後、
   紅燈劇本之前。
2. 手動移除劇本＝事件溯源軟刪除：以移除事件標記，清單與刷新不再包含
   該劇本，歷史檔案保留。
3. MVP 的劇本刷新不計算 Long Call；第七節流程第 6 步隨第九節
   Long Call 比較功能一併生效。
4. 「符合條件的 Spread」之合約品質條件（報價有效性、未平倉量、成交量、
   買賣價差等門檻）沿用現行過濾參數作為預設，未來另行調整；

5. 詳細頁進入時預設選中 baseline 到期日的第 1 名 Spread。
6. 群組（Group）區塊自新版首頁隱藏，底層邏輯保留。
7. 紅燈組內部排序沿用「最後已知最高收益率」規則。
8. 建立劇本時輸入已過完的月份一律拒絕；輸入當月（尚未過完）允許。
9. 同標的多劇本各自獨立刷新、各自原子，不要求共用同一份報價。
