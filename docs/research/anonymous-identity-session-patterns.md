## 給 Owner 看的白話摘要

這張票問的核心問題是：**匿名使用者（沒有帳號、沒有 email、沒有密碼的一般訪客）要怎麼被系統認出「這是同一個瀏覽器回來了」，同時做到夠安全**。答案的核心工具是 **cookie**——瀏覽器幫網站保管的一小段文字，每次連到同一個網站都會自動帶上。本文逐題比較三種把「這是誰」寫進 cookie 的方式、瀏覽器能提供的三層防護、cookie 被偷之後會發生什麼、清 cookie／換裝置的必然後果、要不要給一個「救命碼」讓使用者換裝置後找回劇本，以及未來若要把匿名身份升級成「真的帳號」該怎麼接。

**本文推翻／複雜化的一個直覺**：一開始「只是一串隨機 cookie」聽起來像是一件小事，但 Owner 追加的 **Admin／Superuser** 需求讓事情變得不簡單——因為「隨機 cookie 對到一個匿名 owner」這套機制的安全等級，只要拿掉「這顆 cookie 被偷的後果有多嚴重」這個問題就會被低估。一旦同一套 cookie 機制上面要疊一個「Owner 本人、擁有管理權限」的身份，cookie 被偷的後果就從「看到一個陌生人的幾張劇本」升級成「可能看到全站使用量、甚至能操作管理功能」——本文第七題與 Admin 專節會把這個放大效應講清楚。另一個被複雜化的假設是「未來要接正式帳號」：業界兩家真正有「匿名→正式帳號」機制的廠商（Firebase／Supabase），剛好都不是這張票原本點名要參考 RBAC 做法的那兩家（Auth0／Clerk）——這兩組廠商其實在回答不同的問題，混在一起問容易誤判參考對象。

本文**不做任何決定**——每一題都給「成熟做法」與「代價」，最後一節整理成 Owner 之後開 grilling 票時可以直接拿去問自己的選項清單。

## 目前 Option Chaser 的起點（研究依據，非外部引用）

在回答七道題之前，先把現有程式碼的事實釘住，後面每一題的「代價」都會回頭引用這裡：

- `IdentityResolver = Callable[[], str]`——**零參數**的可呼叫物件，`api_app/identity.py`。production 預設 `default_identity_resolver()` 固定回傳常數 `SOLO_OWNER = "solo"`，不做任何驗證。
- `main.py` 裡 `identity_resolver()` 被**直接呼叫 27 次**（`grep -c` 實測），每一次都是零參數呼叫、沒有任何一處把 `Request` 物件傳進去。
- `Storage` Protocol 有 15 個方法要求**必填、非 `None`** 的 `owner: str` 關鍵字參數，違反時執行期直接 `TypeError`（`require_owner()`，`api_app/storage/__init__.py:473-488`）——這是既有的 fail-closed 保證，跟 cookie 機制怎麼做完全無關、不會被本文任何選項動到。
- `api_app/diagnostics.py` 已經有**兩個**幾乎一模一樣的模式可以直接照抄：`correlation_scope()`／`owner_scope()`，都是 `contextvars.ContextVar` 包成的 `@contextmanager`，在 `main.py` 唯一的 middleware（`_request_scope_middleware`，`main.py:721-732`）裡一起打開，包住 `call_next()`。`emit()`（診斷事件）自己去讀這兩個 ContextVar，不需要任何呼叫端把值一路往下傳。
- 這個 repo**已經有**「跟一般使用者身份完全分開的獨立 secret」先例，而且用了兩次：`CRON_SECRET`（Vercel 排程呼叫用）與 `OPS_SECRET`（`GET /api/ops/metrics` 用），兩者故意不共用同一把——程式碼註解原文：「一個是『Vercel 排程系統呼叫這個 app』的信任邊界，[OPS_SECRET 是]另一種」（`main.py:601-617`）。兩者都是 `Authorization: Bearer <secret>`、fail-closed 401、與 cookie／`identity_resolver` 機制完全無關。
- 全站**目前沒有任何 cookie**——`grep -rn "set_cookie\|Set-Cookie\|request.cookies"` 對 `api_app/main.py` 零命中。
- 全站**目前沒有任何 role／admin 概念**——`grep` 只命中一處：`api_app/storage/backfill.py:46` 的「admin 用途保留的顯式選項」，那是一個**保留給遷移用途的關鍵字參數名稱**，不是角色系統。
- 部署架構（`vercel.json`）：SPA 靜態檔與 `/api/(.*)` 皆由**同一個** Vercel 專案的 rewrite 處理（`destination: "/api/index"`），瀏覽器看到的是**單一 origin**——這件事本身有官方文件佐證，見 Q2。

## 1. Cookie 裡到底存什麼

### (a) 一串隨機、無意義的 id（伺服器查表對到 owner）

**成熟做法**：這是 OWASP Session Management Cheat Sheet 的預設建議形狀——伺服器產生一個隨機值，自己保留一份對照表（session/identity → 使用者），cookie 只帶那個隨機值本身。熵值要求明確：「Session identifiers must have at least 64 bits of entropy」，且必須用 CSPRNG（cryptographically secure pseudo-random number generator）「evenly distributed among all possible values」；若用十六進位編碼，「at least 16 hexadecimal characters long to achieve the required 64 bits of entropy」——關鍵警語是「If any part of the session ID is fixed or predictable, the effective entropy is reduced」（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)，2026-09-11 存取）。OWASP 同時建議**嚴格模式**：「web application will only accept session ID values that have been previously generated by the web application」——不接受使用者自己帶來的 id（同上）。

具體有多安全，Mullvad 的真實案例給了一個可比對的數字感：16 位數字帳號（10¹⁶ 量級，官方原文「a total of 8.99 quadrilion possible account numbers」），在「10 萬個帳號同時在用」的假設下「one would need to guess on average 45 billion times in order to find a working account」（[Mullvad Blog](https://mullvad.net/en/blog/mullvads-account-numbers-get-longer-and-safer)，2026-09-11 存取）——這比 OWASP 64-bit 門檻（純熵值上 2⁶⁴≈1.8×10¹⁹）弱好幾個量級，但因為 Mullvad 這串數字本身就是唯一憑證（沒有伺服器端的「這個帳號還有沒有效」查詢速率限制之外的第二道防線），仍被視為可接受——這說明**「多少熵才夠」跟「這串值還能不能被獨立濫用」是分開的兩個問題**，不能只看熵值本身。

**代價**：這個形狀本身**沒有查表就沒有意義**——伺服器必須維護一份「這個隨機值對到誰」的資料。對 Option Chaser 現有架構而言，這件事幾乎是零額外成本：`owner_id` 本來就會被寫進 `scenarios`／`results`／`snapshots`／`events`／`diagnostics`／`owner_settings`／`owner_credentials`／`owner_verifications` 八張表（CLAUDE.md 既有紀錄，SCALE-06／SCALE-11／SCALE-13），所以「cookie 值直接就是 `owner_id`」（不另開表）或「cookie 值是另一張小表的 key、那張表的另一欄才是 `owner_id`」（另開表）都只是「查表發生在哪一層」的差異，不是「要不要查表」的差異（詳見第 7 題）。**輪換（rotation）**：這個形狀輪換最乾淨——伺服器另外生一個新隨機值、把舊值標記失效即可，OWASP 明文要求「Session ID regeneration is mandatory to prevent session fixation attacks」，且要在「任何權限層級改變」時做（同上），但這條 MUST 的觸發條件是「權限改變」，匿名使用者從頭到尾沒有權限改變事件可以掛，所以「要不要定期輪換一個從未升級過的匿名 cookie」屬於**業界慣例的延伸**，不是 OWASP 這條規則字面上要求的事——這個區分本文後面會反覆用到。

### (b) 有簽章的 token（伺服器不查表也能驗真偽）

**成熟做法**：伺服器用一個只有自己知道的金鑰，對「這是誰＋什麼時候過期」這段內容做簽章（例如 HMAC），cookie 帶著「內容＋簽章」。收到時伺服器重新算一次簽章比對，比對得上就相信內容，**不需要查資料庫**。這種「自我驗證（self-verifying）」的設計省掉了 (a) 的查表成本。

**代價**：省掉查表的代價是**吊銷（revoke）變難**——OWASP JSON Web Token Cheat Sheet 講的正是這個問題（雖然標題寫 JWT，但這條道理對任何「自我驗證、無狀態」的簽章 token 都成立，不只限 JWT 格式）：「if you use JWTs for user sessions, you will need a solution for managing session invalidation. This can be achieved using a deny list of revoked sessions/tokens. If your application implements such a deny list, user sessions won't be completely stateless anymore which might defeat the benefits of stateless sessions」（[OWASP JSON Web Token Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)，2026-09-11 存取）——換句話說：**只要你想要「發現被偷了就能立刻讓那顆 cookie失效」這個能力，你就得幫這個「不查表」的形狀另外做一張查表用的 deny list，等於白繞一圈回到 (a) 的成本，卻沒拿到 (a) 的簡單性**。輪換也比 (a) 麻煩：簽章金鑰本身若要輪換，需要金鑰版本標記（`kid` 之類）與新舊金鑰並存的過渡期，這是 (a) 完全不需要處理的問題。

### (c) JWT（一種標準化的簽章 token 格式）

**成熟做法**：JWT（JSON Web Token）是 (b) 的一種**標準化格式**——結構固定為「`{header}.{claims}.{signature}`，三段各自 base64url 編碼」（[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)，2026-09-11 存取），好處是有現成、經過大量審查的函式庫可以直接用，不必自己刻簽章格式。

**代價**：JWT 繼承 (b) 的全部代價，外加兩個 JWT 特有的坑：

1. **內容是明文可讀的**——OWASP 明講：「JWTs can provide authenticity of the claims (signed JWT) and/or confidentiality of the claims (encrypted JWT)」，簽章版（多數人講的「JWT」）**只保證沒被竄改，不保證別人看不到內容**（[OWASP JSON Web Token Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)，2026-09-11 存取）。任何 owner_id 以外的敏感資訊都不該塞進 JWT payload，除非額外加密（RFC 7519 Security Considerations 原文：「A JWT may contain privacy-sensitive information. When this is the case, measures MUST be taken to prevent disclosure of this information to unintended parties」，[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)，2026-09-11 存取）。
2. **演算法混淆攻擊（algorithm confusion）**——IETF 官方的 JWT 最佳實務文件（RFC 8725）點名這是一個真實發生過的攻擊類別：「The algorithm can be changed to 'none' by an attacker, and some libraries would trust this value and 'validate' the JWT without checking any signature」，並要求「All cryptographic operations used in the JWT MUST be validated and the entire JWT MUST be rejected if any of them fail to validate」（[RFC 8725](https://www.rfc-editor.org/rfc/rfc8725)，2026-09-11 存取）——這不是「用 JWT 就一定會中」，是「用了設定錯誤／太寬鬆的 JWT 函式庫才會中」，但因為 JWT 太流行、市面上壞掉的實作也多，這條紅線值得知道。

**三種形狀對照表**（供 grilling 時快速比較）：

| | (a) 隨機 id + 查表 | (b) 簽章 token | (c) JWT |
|---|---|---|---|
| 需要伺服器查表才能用？ | 是 | 否（驗證免查表） | 否（驗證免查表） |
| 被偷後能立即單方吊銷？ | 是（刪那一列即可） | 否（除非另建 deny list，等於退回 (a)） | 否（同 (b)） |
| 內容對持有者以外的人可讀？ | 不適用（本身無意義） | 視實作（通常不加密） | 是（除非額外加密） |
| 輪換難度 | 低（换新值即可） | 中（需金鑰版本管理） | 中（同 (b)，但多一層函式庫慣例要跟上） |
| 對這個 repo 現有 8 張 `owner_id` 表的相容性 | 完全相容，零額外表 | 需另外設計簽章金鑰儲存位置 | 同 (b) |

## 2. 瀏覽器端的保護

### `HttpOnly`／`Secure`／`SameSite` 分別擋什麼

- **`HttpOnly`**——「A cookie with the `HttpOnly` attribute can't be accessed by JavaScript, for example using `Document.cookie`; it can only be accessed when it reaches the server... This precaution helps mitigate cross-site scripting (XSS) attacks」（[MDN — HTTP Cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies)，2026-09-11 存取）。OWASP 措辭更直接：「Mandatory to prevent session ID stealing through XSS attacks」（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)，2026-09-11 存取）。**【法規／安全必要】**——任何帶身份意義的 cookie 不設這個屬性，就是留一個已知、有名字的漏洞類別開著。
- **`Secure`**——「A cookie with the `Secure` attribute is only sent to the server with an encrypted request over the HTTPS protocol... which means MITM attackers can't access it easily」（[MDN — HTTP Cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies)，2026-09-11 存取）。OWASP：「Mandatory to prevent the disclosure of the session ID through MitM attacks」（同上 OWASP CS）。**【法規／安全必要】**——同樣道理。
- **`SameSite`**——控制 cookie 要不要跟著「跨站（cross-site）請求」一起送出。`Strict` 只在「同站發起的請求」才送；`Lax`（多數瀏覽器沒指定時的預設值，[MDN — HTTP Cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies)，2026-09-11 存取）在 `Strict` 的基礎上，額外允許「使用者從別的網站點連結、直接跳轉過來（top-level navigation）且用安全方法（GET）」時也送；`None` 兩種情況都送，但**必須**同時加 `Secure`（[MDN — Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie)，2026-09-11 存取）。OWASP 提醒這只是**輔助防線**：「Treat `SameSite` as defense in depth against CSRF, not as a replacement for a CSRF token」（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)，2026-09-11 存取）。**【業界慣例＋法規／安全必要混合】**——設 `SameSite` 本身是幾乎零成本的慣例，但「只靠 SameSite 就宣稱擋掉 CSRF」是錯的用法。

### 對本產品的實務限制

Option Chaser 是**同源 SPA**：`vercel.json` 讓靜態檔與 `/api/(.*)` 全部走同一個 Vercel 專案的 rewrite（`destination: "/api/index"`）。Vercel 官方文件對 rewrite 的定義是：「A rewrite routes a request to a different destination without changing the URL in the browser. Unlike redirects, the user won't see the URL change」（[Vercel — Rewrites](https://vercel.com/docs/routing/rewrites)，2026-09-11 存取）——也就是說瀏覽器**永遠只看到一個 origin**，前端呼叫 `/api/*` 從瀏覽器的角度就是普通的同站請求，不需要 CORS，`SameSite=Strict` 在這個架構下**沒有任何實務阻力**（本產品沒有第三方嵌入、沒有跨站表單、也沒有從別的網站直接連進來當作正常操作流程的場景——唯一例外是未來若真的做 email 裡的 claim link，見第 5 題）。

**一個容易被忽略、但真實存在的架構限制**：`vercel.app` 本身是 **Public Suffix List（公共後綴清單，瀏覽器拿來判斷「哪些網域底下的子網域其實是互不相干的不同人」的官方清單）** 上的條目——Vercel 官方知識庫直接證實：「it is not possible to set a cookie at the level of `vercel.app` from your project subdomain」（[Vercel Knowledge Base](https://vercel.com/kb/guide/can-i-set-a-cookie-from-my-vercel-project-subdomain-to-vercel-app)，2026-09-11 存取），理由正是「to prevent supercookies」。這代表：production（`option-chaser.vercel.app`）與分支 preview（`option-chaser-git-claude-imp-....vercel.app`）**是兩個不同的 host**，在 cookie 沒有明確設定 `Domain`（也就是「host-only cookie」，只綁定到設定它的那個確切主機名）的預設行為下，**彼此的匿名身份 cookie 不會互通**——這不是 bug，是 Owner 自己測試工作分支 preview 時就會遇到的必然現象，值得先知道以免誤判成故障。

### Cookie 壽命上限與續命

Chrome 自 M104（2022 年 8 月）起，「Cookies can no longer have an expiration date exceeding 400 days in the future」——超過的值**不是被拒絕，是被降級**：「their expiration date is set to 400 days instead」（[Chrome Developers Blog](https://developer.chrome.com/blog/cookie-max-age-expires)，2026-09-11 存取）。這個上限後來被寫進了 Cookie 規範本身的最新草案（IETF 的 RFC 6265bis，是 RFC 6265 的正式後繼草案，目前仍是 Internet-Draft、尚未定稿為正式 RFC）：「The limit SHOULD NOT be greater than 400 days (34560000 seconds) in the future. The RECOMMENDED limit is 400 days」（[draft-ietf-httpbis-rfc6265bis-22](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22) §5.5，2026-09-11 存取）——這代表**沒有瀏覽器層級的「永久登入」這個選項**，即使不主動設過期時間，也會受這條規則約束。**續命做法**（Chrome 官方文件直接給的解法）：「Developers can extend cookie persistence by resetting cookies with identical names upon user return visits, effectively refreshing the 400-day window」（同上 Chrome Developers Blog）——也就是每次成功的請求都重新送一次 `Set-Cookie`（同名、新的 400 天倒數），只要使用者還在用，這顆 cookie 就不會自然過期；完全不回訪超過 400 天才會真的被清掉。

### `__Host-` 前綴

`__Host-` 前綴是瀏覽器強制的額外保證：「Cookies with names starting with `__Host-` must be set with the `Secure` attribute by a secure page (HTTPS). In addition, they must not have a `Domain` attribute specified, and the `Path` attribute must be set to `/`... This combination yields a cookie that is as close as can be to treating the origin as a security boundary」（[MDN — Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie)，2026-09-11 存取）。因為 Option Chaser 本來就**不需要**（也因 Public Suffix List 而**不可能**）設定 `Domain=vercel.app`，這個前綴幾乎是「免費」的加強——不會犧牲任何本產品目前需要的功能。**【業界慣例，成本近乎零】**

## 3. Cookie 被偷會發生什麼

### 攻擊者能做到哪裡（依這個 repo 現有 domain model 推算）

因為 `require_owner()` 這 15 個方法只認 `owner: str` 這個值本身，不驗證「這個值是不是真的合法持有者送來的」——一旦攻擊者拿到跟受害者一模一樣的 cookie 值，systems 沒有任何額外機制能分辨兩者，攻擊者能做到跟受害者本人一樣多：讀／改／封存／刪除該 owner 名下全部劇本（`scenarios`／`results`／`snapshots`／`events`），以及讀／改／刪該 owner 在 Settings 頁自訂的第三方資料源 **API token**（`owner_credentials`，SCALE-13 既有機制，CLAUDE.md 記錄）——**這一項值得特別點名**：cookie 被偷的後果不只是「劇本外洩」，還包含「使用者自己申請、貼進 Settings 的 Market Data App／其他 provider token 也一起外洩」，資安等級比單純「看到幾張分析結果」高一截。

### 業界緩解手段與各自的誤傷

- **定期輪換**——OWASP 明確要求輪換的觸發條件是「Renew the Session ID After Any Privilege Level Change」（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)，2026-09-11 存取）；但一個從未登入、從未升級權限的匿名使用者**沒有**這種事件可以掛。因此「純粹定期（例如每 30 天）輪換一個匿名 cookie」是**業界慣例的延伸應用**，不是 OWASP 這條規則字面上規定的場景——這個區分值得誠實標出。**【業界慣例】**
- **綁定 IP／User-Agent**——OWASP 承認好處（「Significantly increase the web application detection (and protection) capabilities」），但同一段話立刻給出誤傷來源：「A skilled attacker can bypass these controls by reusing the same IP address assigned to the victim user by sharing the same network (very common in NAT environments, like Wi-Fi hotspots)」，並直接下結論：「Cannot be used by web applications to trustingly defend against session attacks」（同上）。對本產品而言，這個誤傷不是理論——手機使用者在 WiFi／行動網路之間切換、辦公室 VPN 出口 IP 變動，都會讓合法使用者被誤判成「換了一台機器」；若把這種變動當成登出訊號，會直接違背 Owner 對匿名體驗「低摩擦、不用登入」的既有產品定位。**【業界慣例，且有明確、有記載的誤傷】**
- **偵測異常後作廢**——這個手段的前提是「能夠單方吊銷」，回頭對照第 1 題：形狀 (a)（隨機 id + 查表）天生支援，形狀 (b)／(c)（簽章 token／JWT）需要額外的 deny list（OWASP JWT Cheat Sheet 已明講這會讓它「不再完全無狀態」）。

### 業界緩解手段之外，什麼是攻擊者**做不到**的（誠實劃界，非自動保證）

假設 middleware 正確地**只**從已驗證的 cookie 解出 owner（不接受任何使用者自報的 owner 值），攻擊者拿到別人的 cookie 也看不到別人的管理後台或彙總數據（那是另一個獨立的判斷點，見 Admin 專節）；也無法復原已經被永久刪除的資料（垃圾桶語意本身也是 owner-scoped，既有機制不因 cookie 被偷而繞過）。但這兩點都**依賴實作正確**，不是這個機制自動保證的性質。

## 4. 清 cookie／換瀏覽器／無痕模式

### 技術上必然發生什麼

只要匿名身份的唯一根據是「瀏覽器裡的一顆 cookie」，清 cookie／換瀏覽器／換裝置在技術上就**必然**代表「這個瀏覽器不再認得自己是誰」——這不是實作缺陷，是這種機制的定義本身。Supabase 官方文件對自己的匿名使用者機制講得非常直白：「It behaves like a permanent user, except the user can't access their account if they sign out, clear browsing data, or use another device」（[Supabase — Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous)，2026-09-11 存取）——這句話對任何「純 cookie、無 recovery」的匿名機制都成立，不只是 Supabase 自己的產品。

**無痕模式（Incognito）**：Chrome 官方支援頁面明講這是一個**獨立、暫時**的資料集：「During your Incognito session, Chrome temporarily keeps some information, like cookies and site data, to help websites work and support navigation. This information is removed when the Incognito session ends」（[Google Chrome 說明](https://support.google.com/chrome/answer/95464)，2026-09-11 存取）——也就是無痕視窗開著時有自己的一份 cookie（跟平常瀏覽的那份分開），關掉視窗就整份丟棄；下次再開無痕視窗又是全新一個匿名身份，跟上次的無痕身份也不相通。

### 成熟產品怎麼揭露這件事（文案與時機）

- **Firebase 官方部落格明確建議「情境式時機」而非「一開始就講」**：「ask anonymous users to upgrade their account to a full account **when they try sharing data**」，並建議用警告文案：「showing a warning to any user that is anonymous by informing them that they will need to convert to a full user account for certain access」（[Firebase Blog — Best Practices for Anonymous Authentication](https://firebase.blog/posts/2023/07/best-practices-for-anonymous-authentication)，2026-09-11 存取）。同一篇文章也誠實列出風險：「anonymous accounts don't let users have the same account on multiple devices, and anonymous accounts are unrecoverable if the user ever gets signed out」（同上）。**時機原則＝在使用者真的要做一件「換裝置會失去」的事情之前提示，不是一開場就丟一堆警告字**。
- **Mullvad 走的是相反的時機策略——一開始就講清楚、講到底**。帳號號碼頁面本身沒有花俏留言，但當使用者真的走到「找回帳號」流程時，官方文案直接把代價攤開：若透過信用卡付款記錄找回，「If you email us to help resolve a lost account number, you will end up disclosing information about yourself to us (at a bare minimum, your email). If you prefer to remain anonymous, you can instead create a new account」（[Mullvad — Recover lost account](https://mullvad.net/en/account/recover/card)，2026-09-11 存取）——**誠實地把「找回」跟「保持匿名」放在天平兩端讓使用者自己選，而不是假裝兩者都能兼顧**。

## 5. 要不要 recovery code

### Mullvad 式「帳號號碼」

**做法**：帳號號碼本身**就是**唯一憑證（本文 Q1 的形狀 (a) 的極端版本——沒有第二層身份，帳號號碼不對應任何 email／使用者名稱）。「A random account number is generated... this number is the only identifier a person needs」（[Mullvad Blog](https://mullvad.net/en/blog/mullvads-account-numbers-get-longer-and-safer)，2026-09-11 存取）。**Recovery** 不是靠「秘密問題」或「備用碼」，是靠**付款記錄的側門**——且這個側門本身有明確的隱私代價與時間窗（「Accounts are only traceable for 20 days」，需提供卡號後四位／到期日／付款金額與時間，[Mullvad — Recover lost account](https://mullvad.net/en/account/recover/card)，2026-09-11 存取）。

**安全風險與 UX 成本**：安全風險極低（沒有第二個身份聯絡點可以被釣魚／社交工程）；UX 成本是**真的沒有無痛 recovery**——使用者要自己負責保管好那串數字，一旦連付款記錄都找不到，Mullvad 給的建議就是「create a new account」（接受資料全損）。

### Excalidraw 式「分享連結即身份」

**做法**：協作用的加密金鑰在**瀏覽器端**產生，接在分享網址的 `#`（URL fragment）後面——「Anything that's added after the `#` doesn't get sent to the server... Note that we don't send the key to the server!」（[Excalidraw Plus Blog — End-to-End Encryption](https://plus.excalidraw.com/blog/end-to-end-encryption)，2026-09-11 存取）。伺服器上存的是加密後看不懂的資料，只有握有那個網址（含 `#` 後面的金鑰）的人才能解開——**「recovery」等於「有沒有存到那個網址」**，伺服器本身結構上就無法幫忙復原（它從來沒看過金鑰）。

**安全風險與 UX 成本**：對「一張分享出去給多人共同編輯的畫布」這種低風險資料而言是很划算的權衡——沒有帳號、沒有登入摩擦，任何拿到連結的人立即可用；但代價是**連結本身變成完全等同帳號密碼的東西**（誰有連結就有完整存取權，沒有第二層驗證），且遺失連結＝結構性不可回復，跟 Mullvad 一樣。這個模式更適合「單次分享的作品」而非「長期保存、可能含財務／個資的帳號資料」——後者是 Option Chaser 目前的情境（劇本 thesis＋自訂 provider token）。

### Claim link／裝置配對碼

**做法**：這個模式有一份標準化的官方規範可以直接參考——OAuth 2.0 的「Device Authorization Grant」（IETF RFC 8628）：一台裝置顯示一段短碼，使用者在另一台已登入的裝置上輸入那段短碼完成配對。RFC 明文承認這是熵值與易用性的權衡：「The user code SHOULD have enough entropy that, when combined with rate-limiting and other mitigations, a brute-force attack becomes infeasible」，並給出量化範例：「if one uses an 8-character base 20 user code (with roughly 34.5 bits of entropy), the rate-limiting interval and validity period would need to only allow 5 attempts in order to get the same 2⁻³² probability of success by random guessing」（[RFC 8628](https://www.rfc-editor.org/rfc/rfc8628) §5.1，2026-09-11 存取）。

**安全風險與 UX 成本**：安全風險可控（短碼本身弱，但靠速率限制與短時效補強，RFC 本身把這個數學關係講清楚）；UX 成本是**需要使用者同時操作兩台裝置**——這比「換裝置後點一個連結」多一個步驟（要先在舊裝置上生成配對碼），但完全不需要 email，也不留任何第三方（郵件服務商）在信任鏈裡。

### Email magic link 的最輕量版

**做法**：Auth0 官方文件描述的流程：「A user arrives at your application's login screen and enters their email... Auth0 sends a magic link to the user... The user selects the magic link... and automatically logs in」，且連結會過期：「If the user does not access the link within a specific timeframe, the link becomes inaccessible」（[Auth0 — Passwordless](https://auth0.com/docs/authenticate/passwordless)，2026-09-11 存取）。OWASP 的 Forgot Password Cheat Sheet 把這個模式列為四個主要密碼救援手段之一（「URL Tokens」），並給出具體安全要求：token 必須「Randomly generated using a cryptographically safe algorithm」、「Sufficiently long to protect against brute-force attacks」、「Single use and expire after an appropriate period」（[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)，2026-09-11 存取）。

**安全風險與 UX 成本**：這是四個選項裡**唯一需要收集一項個資（email）**的方案，也是唯一真正可能做到「換裝置後不需要任何配對步驟就找回」的方案——代價是安全性繫在「這封 email 本身有多安全」上。NIST 官方的數位身份指引明確點出這個弱點的技術本質（本段引用的是 NIST SP 800-63-3，該文件已被 2025 年 7 月發布的 SP 800-63B-4 取代，措辭是否逐字延續**未查證**——見下方 UNVERIFIED 標記）：「Methods that do not prove possession of a specific device, such as voice-over-IP (VOIP) or email, SHALL NOT be used for out-of-band authentication」，理由是 email 帳號本身不等於「這是同一個人的同一個裝置」（[NIST SP 800-63-3 §5](https://github.com/usnistgov/800-63-3/blob/nist-pages/sp800-63b/sec5_authenticators.md)，2026-09-11 存取）——這條規則是給**聯邦政府等級身份保證**用的門檻，多數消費產品（包括 Auth0 自己賣的 magic link 功能）並不受這條規則約束，但它解釋了「為什麼嚴謹的身份指引普遍認為 email recovery 是較弱的一環」。

**四種模式的風險／UX 對照**：

| 模式 | 安全風險 | UX 成本 | 需要收集個資？ |
|---|---|---|---|
| Mullvad 帳號號碼 | 極低（無第二身份可被社交工程） | 高（真的可能永久遺失） | 否（recovery 側門才需要，且明講會犧牲匿名性） |
| Excalidraw 連結即身份 | 低（無登入摩擦，但連結＝完整存取權） | 遺失連結即不可逆 | 否 |
| 裝置配對碼（RFC 8628） | 可控（熵值＋速率限制的數學關係已標準化） | 中（需兩台裝置同時在手邊） | 否 |
| Email magic link | 依賴 email 帳號本身的安全性（NIST 認為不足以當高保證等級的 OOB 驗證） | 低（單裝置即可完成） | 是（email） |

## 6. 未來升級成正式帳號怎麼接

### Firebase：Anonymous Auth 的 account linking

Firebase 官方文件明確保證 **UID 不變**：「Users are identifiable by the same Firebase user ID regardless of the authentication provider they used to sign in」（[Firebase — Account Linking](https://firebase.google.com/docs/auth/web/account-linking)，2026-09-11 存取）。若目標憑證（例如某個 email）已經綁在另一個帳號上，連結會直接失敗：「Account linking will fail if the credentials are already linked to another user account. In this situation, you must handle merging the accounts and associated data as appropriate for your app」（同上）——**這個合併衝突的處理邏輯 Firebase 完全不幫你做**，文件明講「How you handle this is specific to your application」。另外一個容易忽略的機制：匿名帳號預設 30 天後可能被自動清除，但「If you 'upgrade' an anonymous account by linking it to any sign-in method, the account will not get automatically deleted」（[Firebase — Anonymous Auth](https://firebase.google.com/docs/auth/web/anonymous-auth)，2026-09-11 存取）。

### Supabase：anonymous sign-ins 的 conversion

Supabase 的保證措辭更直接：「After they have been converted, the user id remains the same, which means that any data associated with the user's id would be carried over」（[Supabase Blog — Anonymous Sign-ins](https://supabase.com/blog/anonymous-sign-ins)，2026-09-11 存取）。匿名狀態本身編碼在 JWT 的一個 claim 裡：「An anonymous user can be identified by the `is_anonymous` claim returned in the user's JWT, which is accessible from your Row Level Security policies (RLS)」（同上），讓資料庫層的授權規則可以直接判斷「這筆資料的擁有者現在是匿名還是已升級」，不需要另外查一次身份表。

### Auth0／Clerk：這兩家其實在回答不同的問題

這是本輪查證裡一個值得明講的落差：**票面原本點名參考 Auth0／Clerk 的 RBAC（角色權限）做法，但這兩家官方文件都沒有 Firebase／Supabase 那種「匿名→正式帳號」的第一等公民機制**。Auth0 的 Passwordless 文件全篇沒有任何「訪客／匿名 session」的敘述——所有描述的方式（社交登入、passkey、SMS OTP、email OTP、magic link）都需要某種身份識別子（email、電話、社群帳號），文件裡完全沒有出現「先匿名用、之後才給身份」這個概念。Clerk 的角色模型（見下方 Admin 專節）建立在「使用者已經有身份」之上，同樣不是匿名升級的場景。**這代表 Auth0／Clerk 值得參考的是 RBAC／角色設計本身（見 Admin 專節），而「匿名怎麼升級成正式帳號」這個具體問題，業界的參考架構其實是 Firebase／Supabase，不是 Auth0／Clerk**——這是本文最值得回頭跟 Owner 澄清的一點，避免未來 grilling 時把兩組不同的參考對象混在一起問。

### 現在該預留什麼、什麼完全不用現在做

**該預留（成本低、之後改的代價高）**：Firebase／Supabase 兩家的共同設計核心是「**升級＝在同一個穩定的主鍵上多掛一個事實，不是把資料從一個 id 搬到另一個 id**」。對 Option Chaser 而言，這代表 `owner_id` 這個值本身（不論最終是 cookie 直接當值，還是另一張表的 key）**應該被設計成「升級成正式帳號後也不變」**——升級動作變成「這個 owner_id 現在多了一個已驗證的 email／密碼雜湊／OAuth subject」，而不是「把這個 owner_id 名下 8 張表的資料 UPDATE 成另一個新的 owner_id」。這個決定幾乎零成本，因為 SCALE-06／SCALE-11／SCALE-13 本來就已經把 `owner_id` 設計成一個穩定的字串鍵，本文的建議只是「不要在未來的升級流程裡違反這個既有前提」。

**完全不用現在做**：多 provider OAuth 連結介面；Firebase 自己都承認很棘手、要 app 自己刻的「合併衝突」UI（同一個 email 已經被別的匿名帳號用過怎麼辦）；Supabase 式的 Row Level Security 政策（這個 repo 是直連 Postgres，不是走 Supabase 管理的那一層，這個機制本身就不適用）。這些都屬於「正式帳號」那張未來票的範圍，不是這張匿名身份票要解決的問題。

## 7. 伺服器怎麼把 cookie 對到 owner

### 選項 A：cookie 值直接當 owner id

**做法**：cookie 帶的隨機值，就是寫進既有 8 張表 `owner_id` 欄位的那個字串本身——沒有第二張表。

**對現有結構的影響**：`require_owner()` 與 15 個 Storage 方法的簽章完全不受影響（它們只在乎最後拿到的是不是一個非 `None` 的字串）；不需要新建任何表；改動範圍最小。**代價**：這個字串從此**永遠**以明文形式活在 8 張表裡（且未來若 admin 專節的資料表也採用同一套，會更多）——它不只是「session 值」，還是資料庫裡的**永久外鍵**。這代表**輪換的代價等於重寫每一張有這個值的表的每一列**，操作形狀跟這個 repo 已經做過的 `backfill_owner_ids.py`／`backfill_settings_to_owner()`（CLAUDE.md SCALE-06／SCALE-13 既有紀錄）一樣——是可行的，但比選項 B 侵入性更高。

### 選項 B：另開一張 identity 表

**做法**：cookie 帶的值是一個**session／identity id**，對應到一張新的小表；這張表的某一欄才是真正寫進既有 8 張表的、穩定不變的 `owner_id`。這正是 OWASP Session Management Cheat Sheet 描述的標準形狀本身（session ID → 查表 → 找到使用者），只是把它套用在「cookie → owner_id」這一層，而不是「cookie → 完整使用者物件」。

**對現有結構的影響**：`require_owner()` 與 15 個方法的簽章依然完全不受影響——它們永遠只吃最終那個 `owner_id` 字串，不在乎上游是怎麼解出來的。**好處**：輪換只需要改**這一張新表的一列**（把同一個 `owner_id` 換一個新的 cookie 值），完全不必碰既有 8 張表的任何一列；未來若要支援「同一個 owner_id 同時有兩顆有效 cookie」（例如 claim link 配對出的第二台裝置）、或是要疊 Admin 身份（見下一節），這張表天然是掛新欄位／新關係的地方，不必動 `Storage` Protocol 的既有契約。**代價**：多一張表、多一次查詢（可以在 middleware 裡查一次、整個 request 生命週期只查一次，見下方）。

### 對 `identity_resolver` 這個既有介面的具體影響

這是本題最關鍵、也最具體的部分：`IdentityResolver` 今天的型別是 `Callable[[], str]`——**零參數**。`main.py` 裡 27 個呼叫點全部是裸的 `identity_resolver()`，沒有一處把 `Request` 物件傳進去，也沒有任何一個端點函式的簽章裡有 `Request` 參數可以順手轉傳。這代表：**要讓它認得 cookie，不能簡單改成「多吃一個參數」**——那需要同時改動 27 個呼叫點，外加為每一個目前沒有宣告 `Request` 參數的 FastAPI 端點函式簽章加一個，改動面很大且容易漏改（正是 Admin 專節會提到的「散落判斷」風險的同一種形狀）。

比較低破壞性的路徑，是完全照抄這個檔案裡已經存在、緊鄰在一起的兩個模式——`correlation_scope()` 與 `owner_scope()`（`api_app/diagnostics.py:209-260`）：`main.py` 唯一的 middleware（`_request_scope_middleware`，本來就宣告了 `request: Request` 參數）在 request 一開始就讀 `request.cookies.get(<cookie 名稱>)`，把解出來的值（不論走選項 A 還是 B）放進一個新的 `ContextVar`，包住 `call_next()`；`identity_resolver`（或取代它的新函式）本身維持**零參數**，只是內部改成讀這個 ContextVar，而不是回傳硬編碼常數。**27 個呼叫點與 15 個 Storage 方法的既有契約，理論上一行都不用改**——這是這次研究裡最重要的「好消息」：身份機制的置換，只要遵守既有的 ContextVar 慣例，可以做到低破壞性，不是一次牽動全站的重構。

## Admin／Superuser 身份怎麼疊上去

Owner 已裁示的硬約束：Admin **不是**復活「全站共用 solo」，是一個**正式、獨立**的身份類型；Admin 自己的 Scenario **仍歸屬 Admin 自己的 owner data**（Admin 是「權限比一般人多的一個身份」，不是「脫離 ownership 模型的特權帳號」）。

### 1. Admin identity 如何與一般 ownership 隔離

**成熟做法——「同一個 identity 多一個 role／claim」**：這正是 Auth0 RBAC 的模型：「Permissions: The discrete actions allowed... Roles: A collection of permissions that can be applied to users... Users: Individuals that can be assigned one or more roles」，且權限判定是「additively」的——「if you have overlapping role assignments, your effective permissions are the union of your role assignments」（[Auth0 — RBAC](https://auth0.com/docs/manage-users/access-control/rbac)，2026-09-11 存取）。Clerk 的實際落地是 organization-scoped 的角色：預設有兩個系統角色「**Admin (`org:admin`)** - Offers full access... **Member (`org:member`)** - Offers limited access」（[Clerk — Roles & Permissions](https://clerk.com/docs/organizations/roles-permissions)，2026-09-11 存取）。

**一個值得特別注意的細節，直接影響「要不要把 role 塞進 cookie/JWT」這個問題**：即使 Clerk 是一家原生用 JWT 當 session token 的廠商，它的官方文件明講**系統權限刻意不放進 session token**：「System Permissions aren't included in session claims」，且要求開發者「create Custom Permissions for authorization checks in your application code」若要在後端驗證（[Clerk — Roles & Permissions](https://clerk.com/docs/organizations/roles-permissions)，2026-09-11 存取）。這等於是一家成熟廠商用實際產品設計告訴你：**不要只信任「cookie／token 裡寫的 role」，關鍵授權判斷要在伺服器端另外查一次**——呼應 OWASP 對集中化授權的建議：「Permission should be validated correctly on every request」，且「The technology used to perform such checks should allow for global, application-wide configuration rather than needing to be applied individually to every method or class」（[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)，2026-09-11 存取）。

**成熟做法——「完全獨立的第二套認證路徑」**：這個 repo 自己就有一個現成、已經用過兩次的先例——`CRON_SECRET`／`OPS_SECRET`。兩者都是獨立的環境變數、`Authorization: Bearer <secret>`、字串比對、fail-closed 401，完全不經過 `identity_resolver()`／cookie 機制。程式碼註解已經把兩把 secret 故意分開的理由寫死：一個是「Vercel 排程系統呼叫這個 app」的信任邊界，另一個是不同的信任邊界（`main.py:601-617`）——這證明「完全獨立路徑」在這個 repo 的慣例裡是低成本、被證明可行的選項，不是要另外發明。

**哪種形狀改動最小**：由於 Owner 裁示 Admin 自己的 Scenario 仍歸屬 Admin 自己的 owner data，**單純的「完全獨立第二套認證路徑」自己不夠**——那只能回答「誰可以進 Dashboard」，回答不了「Admin 建立劇本時，這筆資料的 owner_id 是什麼」。因此結構上比較合理的是**混合**：Admin 的瀏覽器仍然拿一顆跟任何人一樣的匿名身份 cookie（所以他自己的劇本走完全正常的 owner-scoped 路徑），**外加**一個獨立、集中判斷的 `is_admin` 旗標——這個旗標**不應該**塞進 `identity_resolver()` 本身的回傳值（它的型別是「這是誰」的 `str`，不該過載成同時編碼「這是誰」與「這個人有沒有權限」兩件不同的事），而應該是一個同樣走 ContextVar 模式、獨立於 owner_id 判斷之外的第二個零參數函式（例如 `is_admin_scope()`／`current_is_admin()`），由同一個 middleware 一次算好。這樣兩個判斷各自單一職責，未來要加第三種角色也不需要碰 `owner_id` 的型別或既有 15 個 Storage 方法簽章。**【Option Chaser 產品選擇，依 Owner 已裁示的硬約束推導】**

### 2. Admin 權限如何避免變成資料隔離漏洞

**常見錯誤模式**：OWASP 直接點名 RBAC 在規模變大後的通病：「In large projects or when numerous roles are present, it is easy to miss or improperly perform role checks」（[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)，2026-09-11 存取）——具體翻譯成這個 repo 的情境：`main.py` 目前有 27 處各自呼叫 `identity_resolver()`，如果 Admin 判斷也走「每個 endpoint 自己記得判斷一次」的散落寫法，未來新增的 Dashboard 端點很容易被漏掉這道檢查（這不是假設性風險——這個 repo 自己的施工紀錄裡就出現過好幾次「`/code-review` 抓到某個新端點漏加某個既有規則」的真實案例，例如 SCALE-06 時期 `owner_id` 洩漏進三個既有端點回應的那次）。

**業界防呆做法**：**單一 authorization checkpoint**（OWASP 原文「global, application-wide configuration」）＋**deny-by-default**：「Even when no access control rules are explicitly matched, the application cannot remain neutral... Adopt a 'deny-by-default' mentality both during initial development and whenever new functionality or resources are exposed by the app」（同上 OWASP CS）。對這個 repo 而言，`identity_resolver` 目前**連 FastAPI 自己的 `Depends()` 依賴注入機制都沒有用**——是裸的模組級函式呼叫。這代表：要幫 Admin 專屬端點建一個「集中判斷點」，勢必要新增至少一個新的檢查機制（不論最後實作成 middleware 前置檢查、FastAPI `Depends()`，或裝飾器），**不能指望現有的呼叫慣例自動生效**——這件事值得先讓 Owner 知道，因為它代表 Admin Dashboard 不是「隨手加幾行 if」就能做對的功能。

**Admin 能不能／該不該看到別人的資料**：這是一個真實的兩難，業界的成熟解法不是「不能看」或「隨便看」二選一，而是幾種節制手段的組合：

- **稽核記錄（audit log）**：Google Cloud 官方針對「客服／工程人員存取客戶資料」這個確切問題，做了一整套產品：Access Transparency——「Access Transparency logs record the actions that Google personnel take when accessing Customer Data」，且記錄內容包含「the affected resource and action, the time of the action, **the reason for the action**, and information about the accessor」，包含「the physical location, employing entity, and job category of the Google employee」（[Google Cloud — Access Transparency 官方文件](https://docs.cloud.google.com/assured-workloads/access-transparency/docs/overview)，2026-09-11 存取）。
- **逐次授權（pre-approval）**：同一份文件講的 Access Approval 讓客戶能**事前**要求核准才放行：「Access Approval lets you authorize requests from Google personnel to access Customer Data」（同上）。
- **遮罩／去識別化**：OWASP 的 Logging Cheat Sheet 對敏感資料的原則是「should usually not be recorded directly in the logs, but instead should be removed, masked, sanitized, hashed, or encrypted」，並建議「personal data de-identification techniques such as deletion, scrambling or pseudonymization」（[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)，2026-09-11 存取）——這條原則延伸到「顯示給 Admin 看」同樣適用：使用者自訂的 provider API token 這類欄位，即使是 Admin 檢視也不該直接顯示明文。同一份文件也明確要求特權操作本身要被記錄：「Use of systems administrative privileges or access by application administrators including all actions by those users」必須記錄，且「All access to the logs must be recorded and monitored (and may need prior approval)」（同上）。

對現在只有一個 Owner 的規模而言，做到「每次跨 owner 查看都留一筆稽核事件（沿用既有 diagnostics／events 機制，只是新增一種事件類型）＋敏感欄位預設遮罩」，成本遠低於做一整套「support engineer 限時授權 impersonation」系統，是合理的最小版本；但**這件事跟 ownership 模型本身要分開**——即使 Admin 查看了某個匿名 owner 的資料，那筆資料的 `owner_id` 依然要保持是那個匿名使用者的，不能因為 Admin 查看而悄悄把 ownership 改寫或併入 Admin 自己的 owner_id 下。**【業界慣例＋法規／安全必要混合，具體節制手段的選擇屬 Option Chaser 產品選擇】**

### 3. 未來 Admin Dashboard 需要的最小安全邊界

**認證方式的兩個選項**：

- **獨立 admin secret**（比照既有 `CRON_SECRET`／`OPS_SECRET`）：新增一個 `ADMIN_SECRET`，`Authorization: Bearer <secret>`，fail-closed。改動量最小——這個 repo 已經做過兩次一模一樣的事。
- **同一套 cookie，多一個 role 判斷**：需要先有第 1-7 題討論的完整 cookie 機制才能疊上去，改動範圍更大，但體驗更好——Owner 不必再多記一個 secret token。

**兩者的後果比較**：一般 owner 的 cookie 被偷，影響範圍是**那一個匿名使用者自己的資料**（劇本、設定、憑證）。Admin 端點被盜用的後果**取決於 Dashboard 到底開放多少**——如果 Dashboard 只讀既有 `operational_metrics`（SCALE-08／#258 既有機制，本身「不分 owner、天級聚合」，零 PII，CLAUDE.md 既有紀錄），被盜用最壞後果是看到全站使用量，跟看到「單一使用者的個人資料」是完全不同量級的傷害；但若 Dashboard 未來擴大到「清理別人的資料」（批量刪除、批量 backfill），後果就從「資訊揭露」升級成「破壞性操作」，量級對齊這個 repo CLAUDE.md 自己記錄的 SCALE-18（#269）「不可逆 cleanup」等級的謹慎——**這正是 OWASP 反覆強調 deny-by-default 與稽核的理由：操作範圍愈大，單一秘密洩漏的代價愈不對稱**。

### 4. admin identity 現在要不要跟 cookie 綁在一起

**Owner 本人也用匿名 cookie、只是多一個 role**：優點是 UX 一致（Owner 不必額外登入，跟一般使用者一樣靠 cookie 過日子），且不需要保存任何額外秘密。缺點：cookie 是這整套機制裡**最容易被偷**的東西（依第 3 題分析——XSS、共用裝置、瀏覽器擴充功能），把 Admin 權限直接掛在同一顆 cookie 上，等於「偷到 Owner 的 cookie」這件事的嚴重度直接從「看到 Owner 自己的劇本」跳到「看到全站彙總數據甚至能操作 Dashboard」——**攻擊面沒變、但傷害半徑放大了**。

**完全另一條路（密碼／magic link）**：觸發 Admin 權限需要「額外提供」一個 cookie 之外的憑證，即使 Owner 的匿名 cookie 被偷，攻擊者仍然拿不到 Admin 權限（前提是這個額外憑證沒有被同一種手法一起偷走，例如沒有也存在同一個瀏覽器的 `localStorage` 裡）。缺點：多了一套要維護的東西（密碼儲存與雜湊，或 magic link 的寄送與過期邏輯）——對「目前只有一個 Owner」的規模，這可能是不成比例的工程投資，呼應這個 repo CLAUDE.md 反覆出現的「避免無謂 scope creep」判斷慣例。

**中間地帶**：獨立 admin secret（`CRON_SECRET`／`OPS_SECRET` 模式）介於兩者之間——不掛在同一顆 cookie 上，但也不是一整套密碼／email 系統，只是「多一個只有 Owner 自己知道的 bearer token」。這件事的實際安全性完全取決於**這個 token 存在哪裡、會不會跟一般 cookie 一起被同一次 XSS 帶走**——這個問題本身值得在 grilling 時明確問 Owner（見最後一節 OD-8）。**本文不給結論，三個選項的代價已如上。**

## 這對 Option Chaser 意味著什麼

- **`SOLO_OWNER` 這個固定字串本身必須退場**——不論最終選哪一種 cookie 形狀，Owner 已裁示「不得恢復全站共用 solo」，這代表 `default_identity_resolver()`「production 預設回傳同一個硬編碼常數」這個現況本身就是要被取代的目標，前面七題的任何答案都要服務這件事，不能倒退回單一固定值。**【Option Chaser 產品選擇，硬約束】**
- **`IdentityResolver: Callable[[], str]` 這個既有介面幾乎不需要改型別**——只需要把它從「回傳硬編碼常數」換成「讀取一個由 middleware 從 cookie 解出、放進 ContextVar 的值」，27 個既有呼叫端與 `require_owner()` 的 15 個方法契約完全不受影響。這是這次研究裡最重要的「好消息」：身份機制的置換，理論上是低破壞性的，只要遵守既有的 `correlation_scope()`／`owner_scope()` 這套 ContextVar 慣例。
- **Admin 應該是「多一個獨立、集中判斷的旗標」，不是「把 admin 塞進 owner_id 字串本身」**——不要讓 `identity_resolver()` 回傳類似 `"admin"` 這種特殊字串再讓每個 endpoint 自己認得這個魔術字串（那正是 OWASP 警告的散落判斷），而是另開一個同樣走 ContextVar 模式的獨立判斷點，在 Admin 專屬端點統一檢查。
- **三個瀏覽器安全屬性在這個同源 SPA 架構下沒有任何實務阻力**——不需要 CORS、不需要跨站分享 cookie，`SameSite=Strict` 加 `__Host-` 前綴幾乎是「免費」的加強。唯一要注意的例外：未來若真的做 email 裡的 claim／magic link，從外部信箱點進來的第一次導覽在 `Strict` 下不會帶上舊 cookie——但這種情境本來就該讓連結自己帶身份令牌，不依賴舊 cookie 存在，所以這不構成非改 `Lax` 不可的理由。
- **400 天 Max-Age 上限代表「永久登入」在技術上做不到絕對永久**，需要「使用者還在用就自動延長」的續命機制（每次成功請求重發 `Set-Cookie`），否則超過一年多沒開的使用者會被悄悄登出而不自知。
- **Vercel preview URL 與 production URL 是不同 host，cookie 不互通**——Owner 自己在分支 preview 上測試時會拿到一個跟 production 不同的匿名身份，這是 Public Suffix List 的必然結果，不是故障，值得先讓 Owner 知道。
- **Cookie 被偷的影響半徑，依現有 domain model，已經涵蓋使用者自訂的第三方 API 憑證**（`owner_credentials`，SCALE-13 既有機制）——這代表這張票的資安等級不只是「劇本被看到」，還包含「使用者存的 provider token 被偷」，這一層在 grilling 時值得明確告知 Owner，不宜輕描淡寫。

OD-4：cookie 被偷之後，要不要做額外的偵測／防護？
這題其實在決定什麼：決定要不要在「純 cookie」之外疊一層行為監控，以及要
承受多少「正常使用者被誤判」的代價。
A：什麼都不做——先接受「cookie 被偷等於帳號被偷」這個現實，靠選 OD-1 的
   A 方案讓「發現了就能作廢」這件事至少可行。
B：加上 IP／裝置指紋比對，不符就要求重新驗證——但 OWASP 自己都說這種
   綁定「不能被信任來防禦」，換 WiFi、用 VPN 的正常使用者會被誤傷。
你的建議：A。這個產品現在的資料敏感度（劇本＋自填的第三方 token）還沒有到
值得犧牲「零登入摩擦」這個賣點的程度。
不現在決定會卡住什麼：不會卡——B 是隨時可以加的進階功能，不影響 MVP。

OD-5：要不要現在就做「recovery／claim」機制，還是先接受清 cookie 就是真的沒了？
這題其實在決定什麼：決定使用者換裝置／清瀏覽器資料後，劇本是不是就真的
找不回來了——這是本票最大的一個產品決定，直接影響第一版能不能上線。
A：現在就做（見 OD-6 選哪一種形狀）。
B：先不做，上線後再看使用者反饋——多數匿名使用者可能根本不介意，先把
   基本的匿名機制做出來，不要卡在這裡。
你的建議：B。這個功能不影響匿名機制本身能不能上線，晚一點做也不會動到
已經存的資料結構（owner_id 設計得好的話，之後隨時可以疊 claim 機制）。
不現在決定會卡住什麼：不會卡住上線，但會卡住「使用者換裝置後找不到自己
的劇本」這個體驗缺口要放多久不管。

OD-6：如果要做 recovery，选哪一種形狀？
這題其實在決定什麼：決定要不要收集 email（多一項個資與維運成本)，還是
維持「完全不收集任何個資」但接受操作稍微麻煩一點。
A：Email magic link——換裝置後最順暢，但要收集 email、要處理寄信，且
   NIST 認為 email 不是夠強的身份驗證手段。
B：裝置配對碼（兩台裝置互相輸入一段短碼）——不收集任何個資，但需要
   兩台裝置同時在手邊，操作步驟比 A 多。
C：像 Mullvad 一樣，直接給使用者一串「救命碼」自己保管——最簡單、零額外
   基礎設施，但完全依賴使用者自己不要弄丟。
你的建議：C 作為第一版最小可行方案（幾乎零開發成本),A 留給之後真的要做
「正式帳號」那張票時一起做（反正屆時就得收 email 了）。
不現在決定會卡住什麼：不會卡上線，但會卡 OD-5 選 A 的話具體要做哪一種。

OD-7：升級成正式帳號的分界，現在要定多細？
這題其實在決定什麼：決定現在的資料庫設計要不要先想好「以後 Owner 可能
加密碼／email」這件事，免得那天要搬資料。
A：現在就把 owner_id 設計成「升級後也不變、只是多掛一個已驗證的 email」
   （成本幾乎是零，只是設計時多想一步）。
B：先不管，以後真的要做時再看情況決定怎麼搬資料。
你的建議：A——這不是多做工作，是同一個工作換一種更省事的做法，Firebase／
Supabase 兩家都是這樣設計的，沒有理由不跟。
不現在決定會卡住什麼：不會卡現在，但選 B 的話，以後真的要做正式帳號時，
要多花一次資料搬遷的工程。

OD-8：Admin 身份要不要跟一般匿名 cookie 綁在一起？
這題其實在決定什麼：決定「Owner 自己的 cookie 被偷」的後果嚴重程度，以及
現在要不要多維護一套獨立的認證機制。
A：Owner 也走同一套匿名 cookie，只是多一個只有 Owner 才有的旗標——體驗
   最一致，但 Owner 的 cookie 被偷，後果從「看到自己的劇本」升級成
   「可能看到全站數據」。
B：完全獨立的一個 admin secret（比照這個 repo 已經用過兩次的 CRON_SECRET／
   OPS_SECRET 模式）——多一個要保管的密鑰，但一般 cookie 被偷不會連帶
   拿到 Admin 權限。
你的建議：B。這個 repo 已經證明過這個模式好用、改動量最小，而且把「一般
使用者」跟「管理權限」的攻擊面徹底分開，是最划算的隔離方式。
不現在決定會卡住什麼：擋住開始寫任何 Admin 專屬端點——沒有這個決定，
不知道那些端點的認證檢查該長什麼樣。

OD-9：Admin 能不能查看其他匿名使用者的資料？要用什麼節制手段？
這題其實在決定什麼：決定「除錯方便」跟「使用者隱私承諾」之間怎麼拿捏，
以及要不要現在就投資稽核機制。
A：完全不能——Admin 只能看彙總數據（像現有的 operational_metrics),
   不能點進任何一個匿名使用者的具體劇本內容。
B：可以看，但每次查看都留一筆稽核記錄（比照既有 diagnostics／events
   機制，只是新增一種事件類型)，且敏感欄位（例如使用者自填的 provider
   token）一律遮罩、不顯示明文。
C：可以看，不設任何額外限制——Admin 就是有完整權限。
你的建議：B。這個產品現在規模小，C 的風險（一旦哪天要多個管理者，或哪天
被盜用）不成比例；A 又會讓「使用者回報問題，Admin 卻看不到內容」這種除錯
場景完全卡死。B 是業界（Google Access Transparency 就是這個思路）驗證
過的中間解。
不現在決定會卡住什麼：不會卡 Admin 身份機制本身能不能先上線，但會卡
「Dashboard 要不要有一個『查看某個 owner 的資料』的功能鈕」這個具體
功能要不要做。

OD-10：Admin 專屬端點現在要建到多完整？
這題其實在決定什麼：決定第一版 Admin Dashboard 的範圍，範圍愈大，
OD-8／OD-9 選錯的代價愈高（回顧本文「操作範圍愈大，單一秘密洩漏的代價
愈不對稱」這條）。
A：先什麼都不做——本票只把「Admin 身份怎麼跟一般匿名身份共存」這個
   機制做出來，Dashboard 本身留給下一張票。
B：先做一個「只讀、只看彙總數據」的最小 Dashboard（例如現有
   operational_metrics 的畫面版）——沒有任何寫入／刪除功能，被盜用的
   最壞後果只是資訊揭露，不是破壞性操作。
C：直接做完整管理功能（查看／編輯／刪除任何使用者的資料）。
你的建議：B。A 會讓「Admin 身份」這個概念做出來卻沒有任何地方用得到，
不利驗收；C 的風險級別直接跳到跟 SCALE-18（#269，不可逆 cleanup）一樣
需要極度謹慎的等級，不該在第一版就衝到那裡。
不現在決定會卡住什麼：不會卡 Admin 身份機制本身，但會卡下一張「Admin
Dashboard」實作票的驗收範圍要寫多大。
