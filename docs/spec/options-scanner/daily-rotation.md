# 分析師資料每日續跑：公平輪替、額度與排程（V2-02／#403）

掃描股票範圍是 S&P 500（503 檔，#404）加上 SU/SA 的自訂清單。這份文件記錄每天怎麼把
它們全部更新一輪、在 Vercel Hobby 的限制下需要多少排程時段，以及排程沒跑時畫面怎麼
照實說。計算規則（共識演算法、兩道門檻、選擇權窮舉、排名）都沒有改。

## 沿用的 #398 機制

全部沒動：成功後同一交易日不重抓；失敗重試 3 次、每次冷卻 15 分鐘；429 時整個來源
暫停（`Retry-After` 與冷卻取較長者，沒有就 30 分鐘）；每日上游上限（一次＝一檔 fetch，
約 2 個 HTTP 請求）；每檔一個處理中標記（120 秒）；續跑游標＝每檔的嘗試紀錄。

## 改了什麼

| 項目 | 之前 | 現在 | 依據 |
|---|---|---|---|
| 每日更新範圍上限 `CONSENSUS_REFRESH_SYMBOL_CAP` | 200 | **600** | 503 檔成分股＋約兩份滿額（各 50 檔）的成分股以外自訂清單 |
| 每日上游上限 `CONSENSUS_DAILY_UPSTREAM_CAP` | 400 | **900** | 600 × 1.5：一整輪之外留約 300 次給失敗重試 |
| 先抓誰 | 固定順序（50 → 自訂 → 其餘），超過 200 的永遠輪不到 | **公平輪替**（下節） | |
| `/api/cron/consensus-refresh` 時段 | 2 個 | **32 個**（下節） | 實測每次 23–30 檔 |
| 排程有沒有跑 | 無從得知 | **排程執行紀錄**（授權成功才記） | |

超出 600 的部分照舊列為「超出每日更新範圍」（`out_of_scope`），畫面照實顯示。截斷順序
仍是 `REFRESH_PRIORITY` 50 檔 → 自訂清單（依代號）→ 其餘成分股，但這個順序**只**決定
誰被截掉，不決定先抓誰。

## 公平輪替

`consensus_cache.rotation_key()`，cron 與 SU「繼續更新」共用（`refresh_symbols()`）：

1. 從沒嘗試過的先；
2. 最久沒嘗試的先（嘗試日，美東）；
3. 同一天嘗試的，資料最舊的先（從沒成功過＝最舊）；
4. 再依嘗試時刻、代號（決定性）。

同一交易日的失敗重試，嘗試日就是今天，所以一定排在所有還沒輪到的後面：重試不會吃掉
首次嘗試的名額。

**保證**：每天的處理量 T＝min(每日上游上限, 當天 cron 時段數 × 每次檔數) > 0 時，每一檔
都會在 **N＝ceil(範圍 ／ T)** 個交易日內被嘗試，任何一檔連續被跳過不超過 N 個交易日。
理由：X 上次在第 d 天被嘗試後，排在它前面的只有嘗試日 ≤ d 的（至多範圍−1 檔）；X 沒輪到
的每個交易日都有 T 檔排在它前面的被嘗試、從此排到它後面。週末沒有 cron，天數以交易日計
（`trading_day()`：週末算週五；不維護假日表，假日照平日跑，最多多抓一次）。

- 正式設定（範圍 503、T ≥ 503）：**N＝1**，每個交易日每一檔都更新一次。
- 測試（`tests/test_consensus_rotation.py`）：凍結時鐘、每日上限 60（遠小於 503），模擬
  30 個交易日（含週末）：N＝ceil(503／60)＝9；每一檔首輪都在 9 個交易日內被嘗試、兩次嘗試
  間隔不超過 9 個交易日、每天剛好用滿上限；上游健康時資料最舊不超過 N 個交易日。
- 失敗的股票：輪替只保證「被嘗試」；上游一直失敗的股票保留上一份成功資料，清單照實標
  資料日期（`as_of`）與失敗原因。

## 本機實測（真實 Yahoo，2026-11-24 10:05–10:20 台灣）

`scripts/consensus_live_build.py --mode cron`：跟 Vercel Cron 同一個端點
（`GET /api/cron/consensus-refresh`）、同一個 45 秒預算，寫入本機 Postgres
（127.0.0.1:55432/oclive403，腳本拒絕非本機主機）；授權用執行時隨機產生的本機值。

| 指標 | 數值 |
|---|---|
| 範圍 | 503 檔（S&P 500，版本 2026-11-08） |
| cron 呼叫 | 19 次（前 18 次每次 23–30 檔、平均 27.2 檔、45.0–47.4 秒；最後一次 14 檔 28 秒） |
| 每檔 | 約 1.7 秒（含 1 秒呼叫間隔） |
| 總時間 | 854 秒（14.2 分） |
| 上游呼叫 | 503 次（＝每檔一次）；HTTP 請求 1007 個（約 2／檔） |
| 失敗 | 1 檔（ERIE：回應缺少 `upgradeDowngradeHistory`），失敗率 0.2%；15 分鐘冷卻後由下一個時段重試 |
| 429 | 0 次（沒有觸發暫停；暫停行為由 `tests/test_api_consensus_update.py` 的 429 測試覆蓋） |
| 同一天再跑一次 | 處理 0 檔、HTTP 0 個 |

一天跑完 503 檔需要 **19 個時段**（503 ／ 27.2）；以觀測到的最少 23 檔計需要 22 個。

## 排程（`vercel.json`）

Hobby：每個 cron 條目每天最多一次、觸發時間在該小時內浮動，每個專案最多 100 個；本專案
函式 `maxDuration` 60 秒，續跑每次預算 45 秒。

- `/api/cron/consensus-refresh` 排 **32 個**時段：UTC 05–12 點與 16–23 點，每小時兩個
  （`0` 與 `30` 分），只在週一到週五（`1-5`）。
  - UTC 05–23 點在美東永遠是同一個週一到週五（EST／EDT 都是），全部算同一個交易日、共用
    同一份每日上限。
  - 避開 13:00–16:00 UTC 的尖峰；每小時最多兩個，就算浮動後重疊，處理中標記也不會重複抓。
  - 容量：32 × 27.2 ≈ 870 檔／天（以最少 23 檔計 736），是 503 檔的 1.7 倍（1.46 倍）：
    一輪跑完之後還有時段處理冷卻過的重試。摘要（UTC 13 點）之前有 16 個時段（368–435 檔）。
- 其他 cron（利率預熱、匿名清理、每日摘要）照舊，總數 35 個。
- 函式用量（官方 Hobby 額度：每月 100 萬次呼叫、4 小時 active CPU、360 GB-hrs）：每天約
  20 次有效呼叫 × 46 秒 ≈ 15 分鐘 wall time，大部分在等網路；在額度內。

## 排程要真的跑：`CRON_SECRET`

Production 目前沒有 `CRON_SECRET`，所以每個 cron 都被 `_cron_authorized()` 回 401。
程式**不**放寬：沒有 secret 就拒絕，不接受 `x-vercel-cron`／User-Agent 這種可偽造的 header。
Owner 的設定步驟在 [`docs/deploy-vercel.md`](../../deploy-vercel.md)「啟用排程」一節。

在那之前畫面與摘要照實說：

- 每次**授權成功**的 cron 執行記一筆 `consensus_cron_run_count`（`count`＝1、`amount`＝這次
  處理的檔數；`operational_metrics`，保留 30 天）。被 401 的呼叫什麼都不寫。
- `GET /api/opportunity/consensus/status` 的 `cron`：`runs_today`、`symbols_today`、
  `last_run_day`（30 天內最近一次；`null`＝排程尚未執行）。
- 機會搜尋頁「資料狀態 → 排程」：「今天已執行 N 次（處理 M 檔）」／「今天尚未執行；最近
  一次在 …」／「排程尚未執行（近 30 天沒有紀錄）」。沒有紀錄時，重試用完或達上限的說明
  改成「排程尚未執行，不會自動更新，明天請手動『繼續更新』」，不再說「明天自動更新」。
- 每日摘要「分析師共識更新」多兩行：「尚未輪到：X（每日更新範圍 Y 檔）」與「排程：…」。
  （每日摘要本身也是 cron，`CRON_SECRET` 沒設時它也不會寄。）
