## 2. 各階段細節與驗收標準

### P0 資料源與樣本量測（Wayfinder task 票）

- **做什麼**：Owner 取得金鑰；離線腳本對約 50 檔計算共識數值與自身歷史序列。
- **驗收**：
  1. 每檔都能列出目前有效的個別目標價（含發布日）。
  2. 能重建至少 24 個月度取樣點的歷史分歧度序列的股票比例 ≥ 80%（不足者列出原因）。
  3. 報告預設門檻（20%／10%）下通過幾檔、每個資料品質條件各排除幾檔。
  4. 報告每檔的 API 呼叫數與耗時，推估 500 檔每日更新的成本。
  5. 腳本不連 Production、不寫任何資料庫（比照 回報#141 的教訓，開跑前先確認連線對象）。

### P1 共識計算核心

- **做什麼**：一個沒有 I/O 的純函式模組。輸入：個別目標價清單（分析師、目標價、發布日）＋
  歷史清單＋規則參數；輸出：平均、標準差、分歧度、歷史序列、百分位、每道門檻的通過與否與
  未通過原因。
- **驗收**（全部是單元測試）：
  1. 手算案例：平均 120、標準差 9 → 分歧度 7.5%。
  2. 百分位：60 個歷史點中 9 個 ≤ 今天 → 15% → 通過 20% 門檻；改成 10% 門檻 → 不通過。
  3. 兩個門檻互相獨立：只調其中一個，另一個的判定不變。
  4. 邊界：剛好等於門檻、分析師人數不足、歷史點不足、全部目標價相同（分歧度 0）、目標價過舊。
  5. 每位分析師只取最新一筆；超過有效期的不計。
  6. 相同輸入必得相同輸出（決定性）。

### P2 資料源 adapter 與共用快取

- **做什麼**：把資料源回應轉成 P1 的輸入；結果存進全站共用的快取表（每個 symbol 一列，
  每個交易日最多抓一次，比照 `dividend_cache` 的 `market_day`／`attempted_day` 寫法）；
  每日更新。
- **驗收**：
  1. adapter 的解析用固定的回應樣本測試（比照既有 `tests/fixtures`），不在測試中連外。
  2. 同一個交易日重複呼叫不會重複打上游。
  3. 上游失敗時保留上一份成功資料並標示日期，不讓整個搜尋失敗。
  4. 每次上游呼叫都經過既有的額度與熔斷機制，或有自己明確的每日上限（依 Q-E）。
  5. 快取表不含 `owner_id`（它是共用市場事實，與刪除使用者資料的流程無關）；表清單的漂移
     防護測試同步更新。
  6. 後端全套測試（含真 Postgres）通過。

### P3 共識劇本與跨標的搜尋後端

- **做什麼**：新端點。流程：讀共用快取 → 套用使用者的兩個門檻 → 對通過的標的產生
  Consensus Scenario（目標價＝平均目標價；目標月份依 Q-C）→ 逐檔抓鏈並呼叫既有內部
  `_analyze()` → 只留下每個策略家族代表候選的摘要列 → 跨標的排序 → 回傳，並帶 `remaining`
  供前端續跑。
- **驗收**：
  1. **等價性**：同一份鏈快照下，搜尋器某檔的結果，與手動建立相同
     （symbol、target_price、target_month、strategies）劇本的結果逐欄相同。
  2. 既有 API 契約測試、引擎數值基準測試全數不變（搜尋器不改引擎）。
  3. 續跑：小預算下分多次完成，結果不遺漏、不重複（比照既有 Refresh Run 的測試寫法）。
  4. 一檔失敗（抓鏈失敗、零合格候選）不影響其他檔，並回報原因。
  5. 不把完整 view 寫進資料庫（既有量測：三個家族的 view 約 12 MiB／次）。
  6. 排序：固定輸入下的排序結果與預期一致；門檻改變時通過名單即時改變、不重抓資料。
  7. 回應欄位名稱不出現 expected／probability 這類字眼（條件情境報酬 ≠ 期望值）。

### P4 Settings

- **做什麼**：使用者設定的儲存與 API；Settings 頁新增「機會搜尋」區塊。
- **驗收**：
  1. 兩個門檻各自獨立儲存、各自可調；未設定時回傳預設 20%／10%。
  2. 輸入驗證（範圍、型別）；既有 Settings 行為與角色分層不變。
  3. 既有使用者的設定讀回來不受影響（新增鍵是選填）。
  4. 前端單元測試＋typecheck＋build 通過。

### P5 搜尋頁、結果頁、存成劇本

- **做什麼**：`#/search` 路由與導覽；通過共識的標的清單；結果表（逐檔出現）；點一列
  「存成劇本」建立普通 Scenario 並進入現有詳細頁。
- **驗收**：
  1. e2e：設定門檻 → 進搜尋頁 → 看到通過清單 → 搜尋 → 結果逐檔出現 → 存成劇本 →
     詳細頁的頭條數字與結果表那一列一致。
  2. 存成劇本受既有的劇本額度限制，超過時顯示既有的訊息。
  3. 文案檢查：頁面沒有「期望報酬」「勝率」「預期獲利」等字眼；有一句說明這是「分析師平均
     目標價成立時」的報酬。
  4. 手機與桌面版面無水平捲動（比照既有 e2e 檢查）。
  5. 既有 e2e 全數通過。

### P6 擴到完整母體

- **驗收**：
  1. 500 檔的每日共識更新在平台限制內完成（單次跑不完時能接續），並有監控數字。
  2. 一次使用者搜尋的上游呼叫數有上限，不會耗盡全站每日額度。
  3. 每日摘要多一段：更新成功／失敗檔數、通過門檻的檔數。

## 4. 尚未解決的重大問題與建議

| # | 問題 | 為什麼重要 | 老弟建議 |
|---|---|---|---|
| 1 | **顯示授權（最重大）** | 查到的自助方案**全部**不允許把資料或衍生數值顯示給公開使用者；正式對外要另談授權，價格未知（已知上限約 US$15,000／年） | ~~先以個人使用方案（約 US$99／月）做成只有 Owner 自己能用的版本~~ **已被 US$0 預算取代**：見 #389 §10、§12 的阻礙 B1–B3 與免費替代路線 R1–R5 |
| 2 | 歷史深度 | 第一關完全依賴每檔股票自己的歷史序列 | 研究顯示 Benzinga 歷史自 2011 年起，足夠；P0 用實際資料確認每檔的取樣點數，並從第一天起每日保存自己算出的分歧度 |
| 3 | 兩道門檻同時套用後，通過的檔數未知 | 太少（常常 0 檔）或太多都會讓功能不好用 | P0 量測後由 Owner 決定是否調整預設值 |
| 4 | 長天期到期日稀疏 | 12 個月後附近可能只有少數到期日，六點規則會選到離目標月份較遠的到期日 | 目標月份決策時一併決定是否提示 |
| 5 | 分析師平均目標價偏樂觀是已知現象 | 「目標價成立」這個前提本身不保證發生 | 產品只顯示條件情境報酬並清楚標示；不做機率宣稱 |
| 6 | 成本：誰都能按一下就觸發數十檔抓鏈 | 會吃掉全站每日上游額度 | 執行模型決策；共識數值全站共用、選擇權搜尋限量 |
| 7 | 分割與資料改寫 | 會讓歷史分歧度失真 | P1 規則處理分割；P2 保存原始回應的日期以便追查 |
| 8 | ETF | 沒有個別分析師目標價 | 依 Owner 指示獨立規劃，不在 P0–P6 |
